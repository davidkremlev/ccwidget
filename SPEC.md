# ccwidget — техническое задание, версия 1

Виджет для рабочего стола macOS, показывающий лимиты подписки Claude Code, заполнение окна контекста и прогноз исчерпания недельной квоты.

## Именование

| Где | Значение |
|---|---|
| Репозиторий, формула Homebrew | `ccwidget` |
| Отображаемое имя приложения | `Usage Widget for Claude Code` |
| Имя бандла в Finder | `CCWidget.app` |
| Bundle identifier | `dev.illvminat.ccwidget` |
| Bundle identifier расширения | `dev.illvminat.ccwidget.widget` — часть формата данных, см. 2.2 |
| Префикс типов в Swift | `CCWidget…` |

Разделение намеренное. `ccwidget` попадает в соглашение экосистемы (ccusage, ccstatusline, ccflare) и находится поиском. Отображаемое имя по формуле «X for Y» — описательное использование чужого товарного знака, которое Apple считает допустимым. Слово «Claude» не должно входить в имя бандла и идентификатор.

### В галерее виджетов приложение называется «CCWidget»

**Принято как есть, переименования не будет.** В Finder и в Dock приложение подписано отображаемым именем, а в галерее виджетов — именем бандла. Расхождение известно и объяснимо:

- в галерею попадают только те, кто уже поставил `ccwidget`; для них совпадение подписи с именем пакета — помощь, а не помеха;
- соседи в том же списке подписаны так же, именами пакетов, а не описаниями: 1Blocker, Dropover, Bear;
- переименование бандла завело бы пробелы в каждый путь в скриптах, в CI и в документации.

### Откуда галерея берёт имя

Установлено опытом; в документации Apple этого нет, и следующий читатель потратит на выяснение столько же, сколько было потрачено здесь.

**Галерея берёт имя из имени бандла на диске.** Ни `CFBundleName`, ни `CFBundleDisplayName`, ни одноимённые поля расширения на подпись не влияют.

Что именно исключено и чем:

| Кандидат | Значение у нас | В галерее | Вывод |
|---|---|---|---|
| `CFBundleDisplayName` приложения | `Usage Widget for Claude Code` | не показано | исключено |
| `CFBundleName` приложения | `CCWidget` → заменено на `Usage Widget for Claude Code`, пересборка и переустановка | подпись не изменилась | исключено опытом |
| `CFBundleName` расширения | `CCWidgetExtension` | не показано | исключено |
| `CFBundleDisplayName` расширения | `Usage Widget for Claude Code` | не показано | исключено |
| Имя бандла на диске | `CCWidget.app` | `CCWidget` | остаётся единственным |

Доказательство от соседей. Перебраны все бандлы в `/Applications` и `/System/Applications`, у которых есть расширение с точкой `com.apple.widgetkit-extension`; ниже те, чью подпись в галерее я сверил глазами с полями на диске:

| Приложение | В галерее | `app.Name` | `app.Display` | `ext.Name` | `ext.Display` |
|---|---|---|---|---|---|
| 1Blocker | 1Blocker | 1Blocker | — | MacWidgetExtension | MacWidget |
| Bear | Bear | Bear | — | Bear Widgets Extension | Bear Widgets |
| Developer | Developer | Developer | — | Developer Widget | Developer |
| Dropover | Dropover | Dropover | — | RecentShelvesWidgetExtension | RecentShelvesWidget |
| Stats | Stats | Stats | — | — | Widgets |
| MindNode | MindNode | MindNode | MindNode | MindNode Widget Extension | MindNode Widget |
| Unread | Unread | Unread | Unread | UnreadWidgetExtension | Unread Widget |
| **CCWidget** | **CCWidget** | CCWidget | Usage Widget for Claude Code | CCWidgetExtension | Usage Widget for Claude Code |

Поля расширения соседи исключают сами: у Bear в галерее «Bear», а не «Bear Widgets»; у Stats — «Stats», хотя `ext.Display` там «Widgets», а `ext.Name` вовсе нет. Имя бандла и `CFBundleName` у них совпадают, поэтому эти два кандидата соседи не различают — различает только наш случай, единственный, где поля разошлись, и различает опытом: `CFBundleName` был заменён, подпись не изменилась.

Полезный контрпример — системный `Clock.app`: `CFBundleName` у него отсутствует вовсе, только `CFBundleDisplayName`, и в галерее он подписан нормально и локализованно. Значит `CFBundleName` не обязателен и запасной путь у галереи есть.

**Кэш имён исключён, и это вывод из наблюдения, а не предположение.** В том же обновлении списка, в котором подпись осталась прежней, иконка в этой самой строке сменилась с заглушки на настоящую. Запись перечитывается; будь дело в замороженном кэше, не обновилось бы ни то, ни другое.

## 1. Зачем это нужно

Существующие инструменты (ClaudeBar, CCSeva, ClaudeUsageBar, ccusage) живут в строке меню или в терминале. Виджета на рабочем столе нет ни у кого. Прогноза исчерпания квоты нет ни у кого, включая встроенные команды `/context` и `/usage`.

Две эти вещи и есть причина существования проекта. Всё остальное — паритет с конкурентами.

**Целевой пользователь:** подписчик Claude Max или Pro на macOS, который упирается в недельный лимит и хочет видеть остаток без единого клика.

## 2. Ключевые архитектурные решения

### 2.1 Источник данных

Claude Code передаёт скрипту статуслайна JSON на stdin при каждой перерисовке. Схема проверена на версии 2.1.220, поля подтверждены живым снимком.

Доступно:

| Поле | Тип | Что даёт |
|---|---|---|
| `rate_limits.five_hour.used_percentage` | Int или Double | Пятичасовое окно, % израсходовано |
| `rate_limits.five_hour.resets_at` | Int | Unix-время сброса, секунды |
| `rate_limits.seven_day.used_percentage` | Int или Double | Недельное окно, % израсходовано |
| `rate_limits.seven_day.resets_at` | Int | Unix-время сброса, секунды |
| `context_window.used_percentage` | Int, Double или null | Заполнение контекста, % |
| `context_window.total_input_tokens` | Int | Токенов в контексте |
| `context_window.context_window_size` | Int | Размер окна, обычно 200000 или 1000000 |
| `context_window.current_usage.cache_read_input_tokens` | Int | Прочитано из кеша |
| `context_window.current_usage.cache_creation_input_tokens` | Int | Записано в кеш |
| `cost.total_cost_usd` | Double | Стоимость сессии |
| `model.display_name` | String | Например `Opus 5 (1M context)` |
| `effort.level` | String | `low` / `medium` / `high` |
| `workspace.repo.name` | String | Имя репозитория |
| `workspace.current_dir` | String | Текущая папка |
| `session_id` | String | Идентификатор сессии |
| `version` | String | Версия Claude Code |

**Недоступно и добываться не будет:**

- Недельный лимит по конкретной модели (в JSON только два общих окна).
- Разбивка контекста по категориям (System tools, MCP tools, Skills и прочее) — это внутреннее представление команды `/context`.

**Проценты приходят не всегда целыми.** Столбец «Тип» выше описывает намерение, а не гарантию: живой снимок принёс `"used_percentage": 28.000000000000004`. Строгий разбор в `Int` на таком значении падает, и мягкий разбор из раздела 6 молча терял окно целиком — виджет рисовал прочерк при исправных данных. Поэтому экспортёр округляет проценты до целых на записи, а модель дополнительно умеет принять и дробное. Одной защиты мало: округление в экспортёре чинит данные, терпимость в модели — старые снимки и будущие сюрпризы.

**Важно:** блок `rate_limits` появляется только после первого ответа модели в сессии. Сразу после запуска или `/clear` его нет. Парсер обязан это переживать без падения — отсутствие полей штатная ситуация, а не ошибка.

**И приходит он не всем.** Документация статуслайна (`claude-code/statusline.md` в хранилище источников, см. `SOURCES.md`) говорит прямо: `rate_limits` присылается **только подписчикам Claude.ai уровня Pro и Max**, и каждое из двух окон, `five_hour` и `seven_day`, может отсутствовать независимо от другого. Для аккаунта без подписки виджет останется без обеих шкал навсегда — не «данные устарели», а «данных этого рода не будет».

Проект называет этот случай отдельно. `LimitsAvailability` различает три положения: окна пришли; окон нет и ответа модели ещё не было (секунды после запуска, говорить не о чем); ответ был, а окон нет — значит их не пришлют. Признак второго и третьего — заполненность `context_window`: она берётся из ответа модели, поэтому цифра там означает, что круг уже пройден.

На экране это выглядит так: малая плитка целиком занята пояснением, потому что кроме недельной шкалы на ней ничего нет; средняя и большая оставляют строку контекста и стоимость и заменяют пояснением только две шкалы лимитов.

**Панель сообщает наблюдение и правило, а вывод оставляет читателю.** Текст: «Лимиты не пришли. Claude Code присылает их аккаунтам Pro и Max после первого ответа». Вероятная причина — тариф, которому их не присылают, но это утверждение о чужой подписке, сделанное по косвенному признаку: заполненности контекста. Если у подписчика Pro лимиты не пришли по иной причине, уверенная фраза о его тарифе — ложь, сказанная ровно тому человеку, который лучше всех знает, что это ложь. Читатель знает свой тариф; ему достаточно факта и правила.

По той же причине вариант перечисления называется `absentAfterReply`, а не «не присылают этому аккаунту»: имя описывает наблюдённое — окон нет, хотя ответ уже был, — а не вывод из него.

**`context_window.used_percentage` бывает `null`** в начале сессии и после `/compact`, пока не пройдёт следующий вызов модели. Это тот же класс, что и дробный процент: поле есть, значения нет.

Источник для всего абзаца — документация статуслайна, а не наблюдение: там же приведён пример снимка с `"used_percentage": 23.5`.

### 2.2 Обмен через контейнер расширения

Расширения виджетов на macOS **всегда работают в песочнице**, независимо от того, в песочнице ли основное приложение. Прочитать `~/.claude/...` из виджета напрямую нельзя, поэтому нужна общая точка на диске.

Такой точкой служит **собственный контейнер расширения виджета**:

```
~/Library/Containers/dev.illvminat.ccwidget.widget/Data/Library/Application Support/ccwidget/
├── snapshot.json      # текущее состояние, перезаписывается
└── history.jsonl      # временной ряд для прогноза, дописывается
```

Расширение читает этот каталог как свой контейнер — доступ к нему песочница даёт всегда и безусловно, это и есть определение контейнера. Приложение и экспортёр обращаются к тому же каталогу по абсолютному пути: приложение не в песочнице, а экспортёр — обычный процесс пользователя.

**Путь вычисляется по-разному внутри песочницы и снаружи, и это обязательно.** Внутри песочницы домашний каталог процесса **и есть** его контейнер: `NSHomeDirectory()` возвращает `…/Containers/dev.illvminat.ccwidget.widget/Data`. Снаружи домашний каталог — обычный `/Users/имя`. Поэтому расширение достраивает к своему дому только `Library/Application Support/ccwidget`, а приложение и экспортёр — весь путь начиная с `Library/Containers`.

Соблазн написать одну формулу на всех приводит к удвоенному пути вида `…/Containers/…/Data/Library/Containers/…/Data/…`. Проверено на живом виджете: ошибка выглядит как «снимок не найден» и без лога неотличима от отсутствия данных.

**НЕПРОВЕРЯЕМОЕ АВТОМАТИЧЕСКИ.** Обе половины ветки покрыты по отдельности: параметрический `exchangeURL(home:)` проверяется в `Tests/`, а поведение внутри песочницы наблюдалось на живом расширении. Не покрыт сам выбор ветки — предикат `isSandboxed`.

*Что именно мешает проверить:* `isSandboxed` выводится из окружения процесса, а тестовый бандл в песочнице не исполняется. Чтобы проверка что-то доказывала, её пришлось бы запускать внутри процесса с той же подписью и теми же правами, что у расширения виджета, — то есть внутри самого расширения, куда тестовый каркас не встраивается. Подделать предикат значит проверить подделку: ветка выбиралась бы не тем, чем в бою. Единственная настоящая проверка этого места — запуск виджета на рабочем столе, и он остаётся ручным.

#### Почему не App Group

App Group — очевидное и рекомендованное Apple решение этой задачи, и оно было реализовано первым. Оно не работает при ad-hoc подписи.

Проверено на живой системе: расширение виджета получает от `containermanagerd` путь к контейнеру группы (`container_create_or_lookup_app_group_path_by_app_group_identifier: success`), но ядро не выдаёт ему доступ — отказ `EPERM` и на чтение файла, и на листинг каталога. При этом обычное приложение в песочнице с теми же entitlements тот же контейнер читает без проблем. Разница именно в том, что расширение — не приложение.

Обзор сторонних виджетов на машине показал, что все работающие подписаны настоящей командой разработчика: три из четырёх используют идентификатор группы с префиксом Team ID, один — без префикса, но и он подписан командой.

**НАБЛЮДЕНИЕ, НЕ ДОКУМЕНТИРОВАННОЕ ПОВЕДЕНИЕ.** Отказа App Group при ad-hoc подписи Apple нигде не описывает: `apple/security-sandbox-file-access.md` рассказывает про групповые контейнеры и про запрос разрешения, но про `EPERM` у расширения с ad-hoc подписью не говорит ни слова. Всё, что здесь написано, получено на этой машине и может быть следствием чего-то, чего мы не видим. Если понадобится опереться на это в решении — воспроизводить заново, а не цитировать абзац.

Вывод: App Group для этого проекта означала бы обязательное платное членство в Apple Developer Program у **каждого, кто собирает из исходников**. Для инструмента, который ставится через Homebrew и правится желающими, это неприемлемая цена. App Group отвергнута.

Побочная выгода отказа: из entitlements ушло единственное ограниченное разрешение, и проект теперь собирается ad-hoc вообще без учётной записи разработчика — без `PROVISIONING_PROFILE_REQUIRED` и `PROVISIONING_PROFILE_SUPPORTED`. У расширения остаётся `com.apple.security.app-sandbox`, у приложения entitlements нет вовсе.

#### Принятые риски

**Запись в чужой контейнер не санкционирована Apple явно.** Каталог принадлежит расширению; то, что посторонний процесс пользователя может туда писать, — следствие обычных прав доступа, а не задокументированная гарантия. Apple вправе ужесточить это в любой версии macOS, например потребовав TCC-разрешения на `~/Library/Containers`. Риск принят сознательно: альтернатива — платное членство для всех, кто собирает проект.

**Путь завязан на bundle id расширения.** Смена `dev.illvminat.ccwidget.widget` меняет каталог и означает потерю накопленной истории, а с ней и прогноза, пока не наберётся новая. Идентификатор расширения следует считать частью формата данных и без нужды не трогать; при вынужденной смене историю надо переносить осознанно.

#### Порядок создания контейнера

Что контейнер заводит система при первом запуске, документировано (`apple/security-sandbox-file-access.md`). Всё остальное в этом подразделе — наблюдение: **запрета создавать контейнер снаружи Apple не публикует**, и вывод о поведении `containermanagerd` сделан по одному случаю на этой машине.

Контейнер заводит система при первом запуске расширения. **Создавать его снаружи запрещено:** `containermanagerd` может счесть заранее созданный каталог чужим и увести его в сторону, после чего расширение окажется в другом месте, а экспортёр продолжит писать в пустоту.

Отсюда требование к установщику: перед подстановкой пути он **обязан проверить, что контейнер существует**, и при его отсутствии сказать прямо — «сначала добавьте виджет на рабочий стол, затем повторите настройку». Молча создавать каталог запрещено. Проверяется наличие `Data/Library/Application Support` внутри контейнера: этот подкаталог создаёт система, и по нему видно, что контейнер настоящий, а не чей-то самодельный.

Сам экспортёр несёт ту же защиту: если родительского каталога нет, он завершается, ничего не создавая. Подкаталог `ccwidget/` внутри уже существующего контейнера он создаёт сам — это часть контейнера, а не контейнер.

#### Как скрипт узнаёт путь

Экспортёр хранится в репозитории как шаблон `Scripts/ccwidget-export.py.template` с плейсхолдером `__GROUP_DIR__`. При установке приложение подставляет вычисленный путь и кладёт результат в `~/.claude/ccwidget-export.py`. Механизм подстановки не менялся с первой версии — сменилось только вычисляемое значение. Ручная установка тоже возможна: путь показывается на экране первого запуска.

### 2.3 Бюджет обновлений WidgetKit

WidgetKit жёстко ограничивает частоту перерисовки — порядка нескольких десятков обновлений в сутки на виджет. Наивная схема «перечитывать файл раз в 30 секунд» не заработает, система просто перестанет вызывать провайдер.

Правильная схема из двух механизмов:

1. **Предгенерация таймлайна.** Провайдер за один вызов отдаёт серию записей с шагом в одну минуту на ближайшие 30 минут. Все они построены из одного снимка, но с пересчитанным обратным отсчётом до сброса. Обратный отсчёт тикает без единого обращения к диску.
2. **Принудительная перезагрузка при изменении данных.** Демон, обнаружив новый снимок, вызывает `WidgetCenter.shared.reloadAllTimelines()`.

**Бюджет назван цифрой, и часть перезагрузок из него исключена.** Здесь стояло «непроверяемое допущение» о том, что перезагрузки от приложения обходятся дешевле системных. Допущением это быть перестало: `apple/widgetkit-keeping-up-to-date.md` (см. `SOURCES.md`) называет и величину бюджета — для виджета, который человек часто смотрит, **от 40 до 70 обновлений в сутки**, что примерно соответствует перерисовке раз в 15–60 минут, — и список случаев, которые в бюджет не идут. Первый пункт этого списка: **приложение, которому принадлежит виджет, находится на переднем плане**.

**Этот довод был верен до 0.3.3 и перестал быть верным вместе с фоновым режимом.** Здесь стояло: наблюдатель живёт в окне, закрыли окно — наблюдение прекратилось, значит перезагрузок, за которые платят, попросту нет. Наблюдатель теперь живёт в приложении, а приложение может работать весь день позади всего остального.

**Замерено 17 августа на машине владельца, через час после выпуска:** перезагрузки #22–#27, по одной в минуту, `reload budget elapsed`, приложение не на переднем плане. Шестьдесят в час против сорока-семидесяти в сутки — дневная норма кончается до обеда, а симптом описан ниже: плитка замирает до перекатывания бюджета, и система об этом не сообщает никак.

**Отсюда два режима вместо одного, и разделяет их `NSApplication.isActive`, а не «открыто ли окно»:** оговорка в документации про передний план, а окно за терминалом это не передний план.

| | На переднем плане | Позади |
|---|---|---|
| Что считается поводом | любое изменение подписи, включая момент съёмки | только сдвиг одного из трёх процентов или переход свежести |
| Не чаще | раза в минуту | раза в 15 минут |
| Цена | по документации ноль | доля дневного бюджета |

Момент съёмки в фоне поводом не считается намеренно: он меняет в плитке время в подвале, и платить за это долей суток значит купить замершую плитку к обеду. Худший случай в фоне — четыре перезагрузки в час, на практике меньше, потому что нужен сдвиг чисел. Держат это `ReloadRegimeTests`, включая сами константы: 60 и 900 секунд.

**Обещание в интерфейсе исправлено вместе с поведением.** Строка у переключателя говорила «в пределах минуты» — теперь «в пределах минуты, пока приложение на переднем плане, и примерно раз в 15 минут, когда нет». Обещание, которое код перестал выполнять, — такой же дефект, как неверный расчёт.

**Что из прежнего расчёта остаётся верным.** Потолок в одну перезагрузку в минуту — остаётся, но только для переднего плана. Оценка «до шестидесяти в час в часы активной работы» — остаётся арифметикой и ровно поэтому опасна в фоне.

**Что остаётся непроверяемым.** Остаток бюджета Apple по-прежнему не публикует, и отказ в перезагрузке ничем не сообщается — система просто не вызывает провайдера. Поэтому пределы не снимаются: они страхуют случай, которого не видно. По той же причине строка журнала теперь называет режим — `in front, free` или `in background, budgeted`: два режима, неразличимые снаружи, это один режим с дефектом, а «бюджет кончился» и «наблюдатель встал» иначе читаются одинаково.

**Как часто мы прижимаемся к потолку.** Пока момент съёмки не входил в подпись снимка (раздел 2.4), до потолка в одну перезагрузку в минуту доходило редко — по нижней оценке порядка тридцати перезагрузок за 127 часов. После правки поводом стала каждая запись, и потолок выбирается в каждый час активной работы: до шестидесяти в час против прежних долей одной. Потолок не изменился — изменилось то, как часто мы в него упираемся. Из бюджета они вычитаются, когда приложение не на переднем плане, — и именно поэтому в этом случае поводов меньше, а пауза длиннее.

**Симптом, по которому это узнают:** виджет перестал обновляться посреди рабочего дня и через какое-то время ожил сам, без каких-либо действий. Ни ошибки, ни записи в логе при этом не будет — система просто не вызывает провайдера, а потом снова начинает. Увидевшему это надо смотреть сюда первым делом, а не искать дефект в наблюдателе: `SnapshotWatcher` в этом случае исправен и честно просит перезагрузку, которую система молча не выполняет. Первое, что стоит попробовать, — увеличить `minimumReloadInterval`, а не трогать подпись: подпись отвечает на вопрос «изменилось ли видимое», и от бюджета этот ответ не зависит.

Политика в конце таймлайна — `.after(последняя запись)`, чтобы система сама пришла за новой порцией.

### 2.4 Демон и честность данных

Данные приходят только когда работает Claude Code. Это фундаментальное ограничение выбранного источника, и его нельзя маскировать.

**Что демон делает в версии 1:**

- Следит за `snapshot.json` через `DispatchSource` по файловому дескриптору.
- При изменении дёргает перезагрузку виджета.
- Раз в тридцать секунд пересчитывает возраст снимка и обновляет признак свежести. Тик привязан к сетке: он приходится на границы получаса и минуты по абсолютному времени, а не отсчитывается от момента открытия окна. Зачем — ниже, «Возраст меряется по одной сетке».
- Перезагружает таймлайны при запуске приложения.

**Дескриптор приходится переоткрывать.** Экспортёр пишет атомарно, через временный файл и `os.replace`, — значит на месте снимка каждый раз оказывается **новый inode** (наблюдение: номер меняется при каждой записи; документация Python обещает атомарность как требование POSIX и о смене inode не говорит). Источник, привязанный к старому дескриптору, получает `.delete`/`.rename` и дальше молчит. Наблюдатель, написанный наивно, срабатывает ровно один раз, и это выглядит как «файл не меняется».

Отсюда две меры: на `.delete`/`.rename` дескриптор переоткрывается, и параллельно отслеживается сам каталог — он переживает подмену файла и ловит появление снимка, которого ещё нет.

**Перезагружать на каждую запись нельзя.** Статуслайн перерисовывается десятками раз в минуту, и прямое `reloadAllTimelines()` на каждое событие сожжёт бюджет из раздела 2.3 за часы. Поэтому перезагрузка идёт при выполнении обоих условий:

- изменилась **подпись** снимка — тройка процентов пятичасового окна, недельного окна и контекста **и момент съёмки**;
- с прошлой перезагрузки прошло не меньше минуты.

События, попавшие в минутное окно, не копятся в очередь: следующая запись экспортёра разбудит демон снова. Отдельно от этого перезагрузка происходит при переходе свежести через порог — вид виджета меняется, а новых данных при этом нет и не будет.

Это обоснование верно ровно потому, что уровней свежести столько же, сколько видов, и никакие два не рисуются одинаково (раздел 2.4). Пока уровней было четыре, а видов три, оно было ложным для одного порога из трёх: переход `fresh` → `recent` тратил перезагрузку на таймлайн, приходивший неотличимым. Проверка `tickDoesNotReloadWithoutAVisibleChange` держит границу с этой стороны: старение, которое ничего не меняет на экране, перезагрузки не стоит.

**Момент съёмки входит в подпись, и это исправление.** Сначала его там не было, с рассуждением «возраст меняется непрерывно, а рисуется предгенерированным таймлайном без участия демона». Рассуждение верно про то, как возраст *растёт*, и неверно про то, как он *обнуляется*. Приход нового снимка ставит возраст в ноль; таймлайн, который уже на руках у виджета, об этом знать не может и продолжает считать от момента своей сборки.

Наблюдалось: окно показывает «обновлено сейчас», оба виджета рядом — «2 минуты назад». Было отправлено сообщение, контекст вырос с 758 до 759 тысяч токенов и остался на 76 %, ни один из трёх процентов не сдвинулся — и ничто не попросило виджет посмотреть заново.

**Чего это стоит, замерено — с оговоркой о точности замера.** Раз момент в подписи, изменением становится каждая запись, и единственным ограничителем остаётся минута.

На 127 часах настоящей истории: по новому правилу — не больше одной перезагрузки на активную минуту, а активность уложилась в 96 десятиминутных окон, то есть **не более ~960** за период (7,6 в час в среднем по всему промежутку, до 60 в час в часы работы). Это верхняя граница.

По старому правилу на тех же данных — **не менее 30** (0,24 в час). Это нижняя граница, и вот почему: `history.jsonl` несёт только недельный процент, а подпись состоит из трёх, и пятичасовой с контекстом двигаются заметно чаще. Настоящее значение старого правила лежит между 30 и 960, ближе к 30; точнее сказать нечем — полной тройки процентов во времени нигде не сохраняется.

Так что рост реален, а его величина ограничена, но не измерена: от нескольких раз до тридцати.

Потолок при этом не изменился: минута между перезагрузками выбрана в разделе 2.3 именно как допустимый предел, и новое правило его не превышает — оно лишь чаще до него доходит. Если бюджета всё же не хватит, крутить надо `minimumReloadInterval`, а не подпись: подпись отвечает на вопрос «изменилось ли то, что видно», и ответ на него от бюджета не зависит.

**Что это значит для бюджета, разобрано в 2.3** и держится теперь на документированном списке исключений, а не на допущении: перезагрузки при открытом окне в бюджет не идут, при закрытом — идти нечему, потому что наблюдатель живёт в окне. Симптом нехватки бюджета и порядок действий описаны там же; коротко: виджет замер посреди дня и ожил сам — смотреть надо в бюджет, а не в наблюдателя.

**Перезагрузка при запуске приложения** нужна не только чтобы показать свежие цифры сразу. Она страхует случай, когда виджет простоял с устаревшим таймлайном, пока приложение было закрыто. Заменой перезапуска `chronod` при разработке она при этом **не служит** — см. раздел 5.1.

**Демона в строгом смысле нет, а фоновая работа есть — с 0.3.3.** `SnapshotWatcher` живёт в приложении и стартует вместе с ним, а не в `.onAppear` у окна. Приложение не запущено — виджет обновляется только по политике `.after` из раздела 2.3, то есть примерно раз в полчаса. Запущено — в пределах минуты.

Отсюда переключатель в «Подробностях»: `SMAppService.mainApp` регистрирует **само приложение** элементом входа, и при запуске по входу окно не показывается (`LaunchKind`, раздел 2.4 ниже). Помощник рядом с приложением как архитектура закрыт замером — WidgetKit отказывает процессу, который не приложение, `ChronoCoreErrorDomain` 27.

**Выключено, пока не включат, и снимается при удалении.** Элемент входа работает на каждом сеансе, не спросив, — это доверие, которое дают, а не берут по умолчанию. Обратный путь обязателен и есть только один: кнопка «Удалить…» в приложении снимает регистрацию (`StatusModel.LoginRemoval`, три исхода, все три с проверкой). Ни `uninstall.sh`, ни Homebrew этого сделать не могут — станса `login_item` у каска правит список System Events, который регистраций `SMAppService` не видит (прочитано в `cask/artifact/abstract_uninstall.rb`). Удаливший приложение мимо кнопки остаётся с записью, которая ничего запустить не может, потому что бандла нет, — и всё же остаётся. **Не проверено:** убирает ли систему такую запись из «Элементов входа» сама; посмотреть это можно только глазами в System Settings или `sfltool dumpbtm` с правами root.

**Чего демон в версии 1 не делает:** не добывает свежие лимиты при закрытом Claude Code. ClaudeBar решает это запуском CLI и разбором вывода `/usage`. Механизм рабочий, но хрупкий и заслуживает отдельного исследования — вынесено в версию 1.1.

**Как честно показать возраст данных:**

| Возраст снимка | Уровень | Поведение |
|---|---|---|
| менее 60 минут | `fresh` | обычный вид |
| 60 минут — 24 часа | `stale` | цифры приглушаются до `secondary`, к подписи добавляется «данные устарели» |
| более 24 часов | `abandoned` | вместо цифр приглашение запустить Claude Code |

**Правило распространяется на обе поверхности — на виджет и на окно.** В обосновании нет ничего специфичного для виджета, а окно вдобавок то место, где происходит сверка с панелью Usage, и суточной давности проценты там вреднее, чем на плитке.

#### Подпись называет момент съёмки, а не возраст

**«обновлено в 11:50», а не «2 минуты назад».** Пороги остались прежними — час и сутки, — но подпись больше не тикает и не считает.

**Причина не в том, что Apple просит реже перезагружаться.** Она в том, что тикающий возраст врёт между обновлениями, а момент съёмки верен всегда. Виджет перерисовывается не тогда, когда меняется число на экране, а тогда, когда ему разрешает система; надпись «1 минуту назад», простоявшая четыре минуты, — это не потеря точности, а ложное утверждение, повторённое четыре раза. «11:50» остаётся правдой, сколько бы на неё ни смотрели.

Заодно исчезает целый класс расхождений: когда обе поверхности печатали возраст, каждая считала его от своих часов, и они разъезжались (см. ниже, «Согласие двух поверхностей»).

Насколько снимок стар, по-прежнему видно — но цветом и словом, а не цифрой: до часа обычный вид, после часа приглушение и «данные устарели», после суток цифр нет вовсе. Это те же три уровня, что и раньше; изменилась только подпись рядом с ними.

#### Обратный отсчёт до сброса рисует система

`Text(date, style: .relative)` продолжает считать, пока расширение не работает (`apple/widgetkit-dynamic-dates.md` в хранилище источников). Отсчёт не вычисляется нигде: в `RowDetail.reset` лежит момент сброса, и его получает SwiftUI.

Отсюда устройство таймлайна из раздела 2.3: записи ставятся туда, где меняется нарисованное, — на два порога свежести и на моменты закрытия окон, — **и, кроме того, с шагом не крупнее получаса до горизонта в два часа**.

**Вторая часть появилась после дефекта, и без неё первая опасна.** Минутная сетка делала две работы: гнала отсчёт и, побочно, заканчивалась через полчаса, вынуждая систему снова спросить провайдера. Записи по одним порогам сохранили первую работу и молча отменили вторую: замерено 7 августа 2026 на живом снимке — таймлайн доставал на **134,9 часа** вперёд, то есть `.after(последняя)` означало, что провайдера не спросят пять с половиной суток. Все записи в нём несли снимок, прочитанный при построении, и плитка показывала данные двухчасовой давности рядом с окном, показывавшим текущие.

Мостом всё это время служили перезагрузки от наблюдателя, а наблюдатель живёт в окне приложения: закрыли окно — плитка замерла. Логи того дня показывают, чем это кончилось: `widget reload (app launch)` в 13:07, `freshness changed to stale` в 14:08 — таймер жив, — и **ни одного `snapshot changed` до 15:58**, когда приложение запустили заново.

Поэтому у таймлайна теперь две границы, а не одна:

- **снизу** — пять минут между соседними записями, как просит Apple;
- **сверху** — полчаса между соседними и два часа до последней. Последняя запись это и есть политика перезагрузки; она отвечает на вопрос «когда система вернётся», и ответ не должен зависеть от того, открыто ли окно.

Порог за горизонтом не теряется: таймлайн, построенный через два часа, понесёт его, и к тому времени он будет ближе.

Что это стоило:

- **Ширина отсчёта ушла из быстрого яруса проверок.** Строку формирует система, код её не видит, измерять нечего. Замер перенесён в ярус рендеров, `Tests/DynamicDateWidthTests.swift`, и ослабление записано в `Docs/rendering-checks.md` вместе с тем, чем оно закрыто.
- **VoiceOver слышит вычисленный отсчёт, а не нарисованный.** Объявление — строка, и строится оно на момент сборки записи, поэтому со временем расходится с тем, что на экране. Принято сознательно: услышать «3 ч 38 мин» там, где написано «3 ч 12 мин», — узнать правду о другой минуте; не услышать ничего — не узнать ничего.
- **Формат стал системным.** Там, где мы печатали «3 ч 38 мин», система печатает «3 ч 37 мин»: она округляет вниз. Расхождение в минуту с прежними снимками README — ожидаемое, а не дефект.

#### Чья сессия: подпись называет проект, но переключение остаётся

Снимок перезаписывается целиком при каждой перерисовке статуслайна, а статуслайн рисует каждая сессия Claude Code. При нескольких одновременных сессиях в снимке оказываются контекст, стоимость и имя проекта той, что пошевелилась последней.

**Наблюдение, 7 августа 2026.** Опрос снимка раз в три секунды при двух работающих сессиях:

| Время | `sessionId` | Проект |
|---|---|---|
| 09:29:27 – 09:30:04 | `8c49cd25` | ccwidget |
| **09:30:24** | **`c4de9152`** | **another-project** |
| 09:30:44 и далее | `8c49cd25` | ccwidget |

Переключение занимает секунды — оно происходит в пределах одного тика статуслайна, — и так же быстро откатывается. Около двадцати секунд плитка показывала контекст и стоимость чужого проекта. Побеждает последний записавший, подтверждено.

Отдельно замечено: `claude -p` (без интерактивного режима) статуслайн, по-видимому, не рисует — headless-сессия отработала, не тронув снимок. Это наблюдение, не документированное поведение.

**Что сделано.** Подвал среднего размера и заголовок блока деталей большого называют проект вместо «эта сессия»: `ccwidget:` вместо `this session:`. Имя берётся из `entry.projectName` — того же источника, что и подпись у строки контекста, чтобы две подписи не могли назвать разные проекты по одному снимку. Проверка `footerNamesTheSameProject` держит это тождество. Если имени в снимке нет, остаётся прежняя формулировка.

**Что этим не решено, и это остаток, а не мелочь.** Подпись объясняет переключение, но не устраняет его: контекст и стоимость по-прежнему принадлежат последней шевельнувшейся сессии, и человек, смотрящий на плитку, видит цифры чужого проекта — теперь хотя бы подписанные его именем. Величины не становятся «его» от того, что названы.

#### Свежий снимок не обещает свежих лимитов

`rate_limits` приходит с ответом модели и лежит в сессии до следующего ответа — документация статуслайна говорит, что блока нет до первого ответа, значит он приезжает с ответами. Отсюда следствие: сессия пишет то чтение, которое видела **сама**, а не самое новое, и `capturedAt` у такого снимка свежий.

**Замерено 17 августа 2026 на истории этой машины.** 522 записи, семь недельных окон, и **13 шагов назад внутри одного окна** — крупнейший 27 % → 24 % с разницей в шесть минут 7 августа. Расход до сброса падать не может. Округлением это не объясняется: `used_percentage` бывает дробным, но одинаковое округление не теряет три пункта.

**Что с этим делают.** Ничего не выбрасывают. Оценка кладёт взвешенную регрессию и смотрит, насколько прямая описывает точки (раздел 7), поэтому устаревшее чтение стоит уверенности, а не даёт уверенный неверный ответ — ворота для этого и заведены. Чего делать нельзя — молчать: перезагрузка, пришедшая с чтением назад, пишет в журнал `older reading: 7d`. Сторожа держат `OlderReadingTests`, включая случай, который иначе кричал бы каждые пять часов: после сброса процент падать обязан, поэтому сравнение идёт по окну, а не по числу.

**Чего это не объясняет.** Почему чтение оказывается старым — вторая сессия, кеш внутри одной или что-то третье, — по одному замеру не разделить. Записано наблюдение, не причина.

#### Строка перезагрузки говорит, что нарисовано

Было `widget reload #22 (snapshot changed)` — и всё. 17 августа этого не хватило: владелец закрыл одно из двух окон редактора, увидел в пятичасовой строке «закрылось» и спросил, связано ли одно с другим. Ответ требовал знать, было ли окно уже истёкшим в том снимке, — и порядок событий пришлось восстанавливать по метке времени в истории сообщений самого Claude Code.

Теперь строка несёт то же, что рисует плитка: `moved 5h,context · five-hour expired · week open`. Значений в ней нет — проценты это сырые поля, они `.private`, а `.private` без профиля читается как `<private>`, то есть строка из них не ответила бы ни на что. Публично то, что видно на экране: что сдвинулось и в каком состоянии окна. `moved nothing` — законный ответ: перезагрузка бывает и от перехода свежести.

Заодно переименована причина `budget window closed` → `reload budget elapsed`. Она про минутный рацион перезагрузок, а не про окно лимита, и это столкновение слов путало при разборе — в том числе меня.

**Малый размер остаётся без имени.** Там нет ни подвала, ни блока деталей: плитка целиком занята недельным окном, которое принадлежит аккаунту, а не сессии, и переключением не задето. Ограничение известное: если на малый размер когда-нибудь попадёт что-то посессионное, подписать его будет негде.

#### Согласие двух поверхностей: было утверждением, стало тождеством

Здесь стояло правило «окно и виджет обязаны произносить возраст одинаково, посимвольно», и его держала проверка, которая имитировала часы обеих поверхностей и сравнивала строки. Она существовала потому, что однажды окно сказало «обновлено 42 секунды назад» рядом с виджетом, говорившим «1 минуту назад».

Правило снято, и заменено оно не другим правилом, а устройством:

- возраст не печатает никто — обе поверхности печатают момент съёмки, одну и ту же строку из одного поля снимка;
- отсчёт не вычисляет никто — обе передают системе один и тот же `Date` через один и тот же тип `RowDetail`, и рисует их один и тот же `DetailLine`.

Разойтись стало нечему: у двух поверхностей больше нет двух вычислений, которые могли бы дать разные ответы. Проверка, сравнивавшая строки, удалена вместе с правилом; на её месте `Tests/TimelineTests.swift`, который держит форму таймлайна и то, что момент сброса доезжает до вида неискажённым.

**Что взамен потеряно.** Прежняя проверка ловила бы расхождение, если бы оно вернулось. Новая не ловит — она следит за тем, чтобы не появилось второе вычисление, а не за тем, чтобы два вычисления совпадали. Если однажды одна из поверхностей снова начнёт считать сама, поймает это не проверка, а глаз.

**Каждый вариант перечисления обязан производить наблюдаемую разницу в том, на что он должен влиять.** Область ответственности у каждого своя: у свежести — вид, у `Forecast.Outcome` — вердикт на экране, у `Forecast.Gate` — диагноз. Сначала называется область, потом сравниваются варианты попарно. Сторожа живут в `Tests/ObservableDifferenceTests.swift`, по одному на перечисление, каждый проверен подделкой.

**Диагностика — законная область ответственности.** `Forecast.Gate` влияет на вердикт лишь двумя способами: `admitsAVerdict` истинно для `open` и `held`, ложно для `closed` и `withdrawn`. Четыре варианта существуют не ради вердикта, а ради ответа на вопрос «почему», который задают лог провайдера и `ccwidget-replay`. Схлопывать их до двух нельзя: `held` отличает вердикт, стоящий на текущем замере, от вердикта, который держит гистерезис, а `withdrawn` отличает «показывали и убрали» от «не показывали никогда». Именно поразрядная таблица `ccwidget-replay` нашла ложную дату, показывавшуюся 58,8 % времени; средство разбора — такая же поверхность продукта, как экран. Вопрос закрыт, переоткрывать его без новых фактов не нужно.

**Уровней три, потому что видов ровно три.** Их было четыре: `fresh` до пяти минут и `recent` от пяти до шестидесяти. Различие между ними имело смысл, пока подпись говорила «только что» моложе пяти минут; когда формулировка ушла, смысл ушёл с ней, а вариант остался. Различие, не производящее наблюдаемой разницы, — ложь о сложности системы: его надо поддерживать, оно заставляло демон перезагружать таймлайн, возвращавшийся ровно таким же, и держало ниже, в 2.3, обоснование, переставшее быть верным.

Правило, которое пришло на замену: **никакие два уровня не рисуются одинаково.** Виджет рисует себя ровно двумя битами — приглушён или нет, цифры или приглашение; два уровня, совпадающие по обоим, — это один уровень под двумя именами. Закреплено проверкой `everyLevelLooksDifferent`: добавьте четвёртый уровень, и она падает, пока он не станет видимым.

Схлопывание — следствие правки формулировок выше, а не отдельное решение о порогах. Граница в пять минут не передвинута, а упразднена; ближайшая осталась там же, где была, — час.

Виджет, который молча показывает вчерашние проценты — хуже отсутствующего виджета.

**ОТСТУПЛЕНИЕ ОТ РЕКОМЕНДАЦИИ, ПРИЧИНА ЗАПИСАНА.** Human Interface Guidelines
по виджетам просят не прятать устаревшие данные за заглушкой — и тут же просят
показывать, когда данные обновлялись, если человек смотрит чаще, чем виджет
успевает обновиться. Два указания расходятся ровно на нашем случае, и мы
выполняем оба наполовину: возраст показываем всегда, цифры старше суток
убираем. Довод за это — свой, в источниках его нет: процент недельного окна
суточной давности не «устаревшая версия правды», а число, по которому человек
примет неверное решение, потому что за сутки окно успевает и сброситься.
Граница проведена по суткам, а не по «устарело вообще» именно поэтому.

**Пороги проверены наблюдением, а не только проверками.** Раньше вся эта таблица держалась на прогонах; теперь каждая её строка увидена на живом столе.

- **Час.** Цифры приглушились до `secondary`, к возрасту добавилось «данные устарели», бейдж окна встал в «Нужна проверка» — одновременно и согласованно на виджете, в окне и в подписи возраста.
- **Промежуток от часа до суток.** Держится согласованно на всех поверхностях всё время, а не только в момент перехода.
- **Сутки.** Малый виджет: «Данные устарели · 1 день назад». Средний и большой: то же плюс «Запустите Claude Code в терминале, чтобы обновить». Окно: шкал нет, вместо них «Цифрам больше суток. Запустите Claude Code в терминале, чтобы обновить». Ветку окна до этого не видел никто — она написана в этой же серии правок и до сих пор держалась одной проверкой.

**Возраст переживает сон машины.** После ночи и выхода из сна на всех трёх поверхностях стояло согласованное «12 часов»: отсчёт не залип на моменте засыпания и не сбросился. Это стоило проверить отдельно — возраст считается от абсолютного времени, а таймлайн виджета предгенерирован на полчаса вперёд, и оба могли пережить сон по-разному.

**Шапка окна при самом широком бейдже.** «Нужна проверка» и заголовок «Usage Widget for Claude Code» целиком, без многоточия — в точности тот случай, который до правки обрезало.

#### Фоновая свежесть: помощник рядом с приложением не работает

**Замер, 17 августа 2026.** План был такой: маленький исполняемый файл внутри бандла, зарегистрированный как launch agent, с тем же `SnapshotWatcher`, что у окна, — свежесть открытого окна без окна. Написан, собран, положен в `Contents/MacOS/`, запущен. Не работает:

```
widgets:  unavailable — Error Domain=ChronoCoreErrorDomain Code=27
```

и `reloadAllTimelines()` из него не делает ничего. Проверено с контролем: записан свежий снимок, через двадцать секунд плитка показывает прежний; помощник просит перезагрузку; через двадцать пять секунд плитка показывает прежний — сменился только обратный отсчёт, который рисует система.

`Bundle.main` внутри бандла — это приложение (`dev.illvminat.ccwidget`, `/Applications/CCWidget.app`), то есть общего бандла недостаточно. `ChronoCoreErrorDomain` в документации Apple не описан вообще; это измерение, помечено измерением в `SOURCES.md`, и `Tools/ccwidget-widgetkit-probe` восстанавливает факт по требованию.

**Что из этого следует.** Перезагрузить этот виджет может только само приложение. Значит фоновая свежесть — это приложение, работающее в фоне, а не помощник рядом с ним: `SMAppService.mainApp` и окно, которое не открывается при запуске по входу. Отдельный помощник как архитектура закрыт, и закрыт замером, а не мнением.

### Что стало с «одной сеткой» и с расхождением на минуту

Здесь стояли два раздела: как обе поверхности округляют момент до начала минуты, чтобы печатать одинаковый возраст, и почему во время активной работы они всё равно расходятся на минуту.

Оба сняты вместе с тикающим возрастом. Округлять больше нечего — момент съёмки не зависит от того, когда на него смотрят; расходиться тоже нечему — отсчёт до сброса обе поверхности отдают системе, а не считают. Устройство и то, что взамен потеряно, описаны выше, в «Согласие двух поверхностей».

Осталась одна сетка, и она внутри `Freshness`: момент, по которому определяется уровень, по-прежнему округляется `AgeClock.anchor` до начала минуты. Это не про печать, а про порог: без округления виджет и окно пересекают час в разные секунды и приглушаются в разное время по одному файлу.

## 3. Скрипт-экспортёр

Заменяет собой скрипт-разведчик. Пишет два файла: снимок для виджета и строку в историю для прогноза.

Путь: `Scripts/ccwidget-export.py.template`, устанавливается в `~/.claude/ccwidget-export.py`.

В репозитории лежит шаблон, а не готовый скрипт. Плейсхолдер `__GROUP_DIR__` заменяется на реальный путь контейнера при установке — см. раздел 2.2, почему этот путь нельзя знать заранее.

Написан на чистом Python без обёртки на bash. Ранняя версия использовала heredoc внутри shell-скрипта и была сломана: два перенаправления в stdin подряд, побеждает последнее, Python получал данные вместо кода и молча завершался.

```python
#!/usr/bin/env python3
import json, os, stat, sys, time

# Обе подстановки делает установщик:
#   __GROUP_DIR__  — вместе с кавычками, корректным литералом Python
#   первая строка  — абсолютным путём к интерпретатору
GROUP_DIR = "__GROUP_DIR__"

# Больше — не наши данные. Статуслайн присылает килобайты; мегабайт с запасом
# в триста раз, а без предела гигабайтный вход попадал в снимок целиком
# и валил расширение виджета при чтении.
MAX_INPUT = 1 << 20

MIN_INTERVAL = 600  # см. раздел 7: дедупликация истории


def is_regular_or_absent(path):
    """Правда, если по пути обычный файл или ничего.

    Символическая ссылка обычным файлом не считается: запись сквозь неё
    уничтожает файл на другом конце, а экспортёр работает десятки раз
    в минуту с правами пользователя.
    """
    try:
        st = os.lstat(path)
    except FileNotFoundError:
        return True
    except OSError:
        return False
    return stat.S_ISREG(st.st_mode)


def open_new(path):
    """Открывает файл на запись, отказываясь идти по ссылке."""
    try:
        # unlink снимает саму ссылку, а не то, на что она указывает.
        os.unlink(path)
    except FileNotFoundError:
        pass
    except OSError:
        return None
    try:
        fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL | os.O_NOFOLLOW, 0o600)
    except OSError:
        return None
    return os.fdopen(fd, "w")


def open_append(path):
    if not is_regular_or_absent(path):
        return None
    try:
        fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_APPEND | os.O_NOFOLLOW, 0o600)
    except OSError:
        return None
    return os.fdopen(fd, "a")


def last_history_entry(path):
    """Последняя непустая строка истории. Читаем хвост, а не весь файл."""
    try:
        with open(path, "rb") as f:
            f.seek(0, os.SEEK_END)
            size = f.tell()
            f.seek(max(0, size - 4096))
            lines = f.read().splitlines()
        for raw in reversed(lines):
            if raw.strip():
                return json.loads(raw)
    except Exception:
        pass
    return None


def should_append(prev, entry):
    if prev is None:
        return True
    if prev.get("resetsAt") != entry["resetsAt"]:
        return True
    if prev.get("sevenDay") != entry["sevenDay"]:
        return True
    return entry["t"] - (prev.get("t") or 0) > MIN_INTERVAL


def main():
    raw = sys.stdin.buffer.read(MAX_INPUT + 1)
    if len(raw) > MAX_INPUT:
        return
    try:
        d = json.loads(raw)
    except Exception:
        return
    if not isinstance(d, dict):
        return

    # Контейнер расширения заводит система при первом запуске виджета.
    # Создавать его снаружи нельзя: containermanagerd может счесть каталог
    # чужим и увести его в сторону. Родителя нет — виджет не запускался.
    if not os.path.isdir(os.path.dirname(GROUP_DIR)):
        return

    os.makedirs(GROUP_DIR, exist_ok=True)

    rl = d.get("rate_limits") or {}
    cw = d.get("context_window") or {}
    cu = cw.get("current_usage") or {}
    ws = d.get("workspace") or {}
    repo = ws.get("repo") or {}
    md = d.get("model") or {}

    read = cu.get("cache_read_input_tokens") or 0
    write = cu.get("cache_creation_input_tokens") or 0
    total = read + write
    ratio = round(read / total, 4) if total else None

    def pct(v):
        """Проценты приходят то целыми, то дробными: 28.000000000000004."""
        try:
            return int(round(float(v)))
        except (TypeError, ValueError):
            return None

    def window(key):
        w = rl.get(key)
        if not w or pct(w.get("used_percentage")) is None:
            return None
        return {
            "usedPercentage": pct(w.get("used_percentage")),
            "resetsAt": w.get("resets_at"),
        }

    # Раздел 4: пишем только то, что показывается. Полного пути к проекту
    # здесь нет — виджет его не отображает, а выдать он может заказчика.
    session = d.get("session_id")
    session = session[:8] if isinstance(session, str) else None

    snap = {
        "schemaVersion": 1,
        "capturedAt": int(time.time()),
        "sessionId": session,
        "claudeCodeVersion": d.get("version"),
        "model": {
            "id": md.get("id"),
            "displayName": md.get("display_name"),
            "effort": (d.get("effort") or {}).get("level"),
        },
        "project": {
            "name": repo.get("name")
            or os.path.basename(ws.get("current_dir") or ""),
        },
        "limits": {
            "fiveHour": window("five_hour"),
            "sevenDay": window("seven_day"),
        },
        "context": {
            "usedPercentage": pct(cw.get("used_percentage")),
            "totalInputTokens": cw.get("total_input_tokens"),
            "windowSize": cw.get("context_window_size"),
            "cacheHitRatio": ratio,
        },
        "cost": {"sessionUsd": (d.get("cost") or {}).get("total_cost_usd")},
    }

    tmp = os.path.join(GROUP_DIR, "snapshot.json.tmp")
    handle = open_new(tmp)
    if handle is None:
        return
    with handle as f:
        json.dump(snap, f, ensure_ascii=False)
    target = os.path.join(GROUP_DIR, "snapshot.json")
    # os.replace переименовывает саму ссылку, а не идёт по ней.
    os.replace(tmp, target)

    sd = snap["limits"]["sevenDay"]
    if sd:
        hist = os.path.join(GROUP_DIR, "history.jsonl")
        entry = {
            "t": snap["capturedAt"],
            "sevenDay": sd["usedPercentage"],
            "resetsAt": sd.get("resetsAt"),
        }
        if should_append(last_history_entry(hist), entry):
            handle = open_append(hist)
            if handle is None:
                return
            with handle as f:
                f.write(json.dumps(entry) + "\n")


try:
    main()
except Exception:
    pass
```

Требования к скрипту:

- **Никогда не пишет сквозь символическую ссылку.** Временный файл открывается с `O_NOFOLLOW` и `O_EXCL` после `unlink`, история — с `O_NOFOLLOW` и проверкой `lstat`. Экспортёр исполняется десятки раз в минуту с правами пользователя: без этого подложенная ссылка превращает его в средство уничтожения произвольных файлов. Проверено на стенде — файл-жертва остаётся нетронутым, снимок при этом пишется нормально.
- **Читает не более мегабайта со stdin.** Статуслайн присылает килобайты; без предела гигабайтный вход попадал в снимок целиком и валил расширение виджета при чтении. Больше предела — выход без записи.
- **Интерпретатор прибит абсолютным путём.** Первую строку подставляет установщик, `env` не используется: `/opt/homebrew/bin` доступен на запись пользователю, а `#!/usr/bin/env python3` брал бы оттуда.

- **Всегда завершается кодом 0.** Падение экспортёра не должно ломать интерфейс Claude Code.
- **Ничего не печатает в stdout.** Статуслайн остаётся пустым; виджет — единственный потребитель.
- **Пишет атомарно** через временный файл и `os.replace`. Иначе виджет однажды прочитает половину файла.
- **Отсутствие полей — норма.** Ни одно обращение к словарю не должно валиться на `KeyError`.

Подключение в `~/.claude/settings.json`:

```json
{
  "statusLine": {
    "type": "command",
    "command": "/Users/ИМЯ/.claude/ccwidget-export.py",
    "padding": 0
  }
}
```

Тильда в пути не раскрывается — только абсолютный путь.

## 4. Схема снимка

```json
{
  "schemaVersion": 1,
  "capturedAt": 1785310000,
  "sessionId": "e9d4c9d7",
  "claudeCodeVersion": "2.1.220",
  "model": {
    "id": "claude-opus-5[1m]",
    "displayName": "Opus 5 (1M context)",
    "effort": "high"
  },
  "project": {
    "name": "example-app"
  },
  "limits": {
    "fiveHour": { "usedPercentage": 15, "resetsAt": 1785313200 },
    "sevenDay": { "usedPercentage": 61, "resetsAt": 1785376800 }
  },
  "context": {
    "usedPercentage": 5,
    "totalInputTokens": 50467,
    "windowSize": 1000000,
    "cacheHitRatio": 0.4088
  },
  "cost": { "sessionUsd": 0.311 }
}
```

**В снимок пишется только то, что показывается.** Полного пути к проекту здесь нет намеренно: ни один размер виджета его не отображает, а раскрыть он способен многое — путь вида `~/Clients/<имя клиента>/...` выдаёт заказчика любому, кто увидит экран или файл. Пишется только `project.name`, и только потому, что он стоит у строки контекста.

По той же причине `sessionId` усечён до восьми знаков. Полный идентификатор связывает снимок с конкретным файлом транскрипта в `~/.claude`; восьми знаков хватает, чтобы отличить одну сессию от другой при отладке, и не хватает, чтобы служить ссылкой.

Правило общее: **сомнительное поле не защищают, его не пишут.** Защита требует, чтобы все её слои работали одновременно, отсутствующее поле не требует ничего.

Поле `schemaVersion` обязательно. Когда Anthropic поменяет схему статуслайна — а она поменяется — приложение должно уметь отличить старый снимок от нового и не рисовать чушь.

Цель развёртывания: **macOS 14.0**. Ниже не опускаемся, потому что ниже нечем проверять, выше не поднимаем — терять пользователей.

Здесь стояло «виджеты на рабочем столе появились именно там». Источника этому нет: `WidgetFamily` доступен с macOS 11.0, а Human Interface Guidelines называют рабочий стол Mac среди мест, где живут виджеты, не упоминая версии. Работают ли виджеты на рабочем столе в macOS 11–13, никто не проверял. Число 14 держится не на этом, а на образе CI, ниже которого заявленный минимум опускать нельзя.

**Чем это подтверждено.** CI собирает приложение и прогоняет проверки на двух образах: `macos-14` (минимум) и `macos-latest` (текущая). Отдельный шаг читает `minos` из собранного двоичного файла и падает, если он разъехался с заявленными 14.0 — число в конфиге тихо дрейфует, число в бандле нет.

**НЕПРОВЕРЯЕМОЕ В CI.** Сам виджет на macOS 14 и 15 не запускался ни разу. WidgetKit требует рабочего стола и сеанса пользователя, поставить виджет на стол в CI нельзя, а покрытие видов равно нулю. Проверено вручную только на macOS 26. Это помечено непроверенным в README, в разделе требований.

*Что именно мешает проверить:* WidgetKit рисует виджет только на рабочем столе вошедшего пользователя, а поставить виджет на стол нельзя ни командой, ни API — только перетаскиванием из галереи. У образов CI сеанса с рабочим столом нет. Обойти это удалось бы лишь запуском на настоящей машине с macOS 14 или 15, которой нет ни у кого из участников; ярус 3 из `Docs/rendering-checks.md` закрывает отрисовку видов, но не поведение WidgetKit.

**Правило: заявленная минимальная версия не может быть ниже проверяемой в CI.**

Это не отдельное решение, а следствие того же правила, по которому живёт вся документация проекта: `README` и `SPEC` описывают проверенное, а непроверенное помечается непроверенным явно. Строка «macOS 14 или новее» в требованиях — это обещание. Обещание, за которым не стоит прогон, ничем не отличается от догадки, а читатель отличить их не может.

Отсюда механика: **уходит образ — поднимается минимум.** Не «оставляем 14 и пишем оговорку»: оговорка про непроверенную минимальную версию не помогает тому, кто на неё смотрит, — он всё равно не знает, работает у него или нет, и узнает это установкой. Числу в требованиях либо есть чем отвечать, либо его там быть не должно.

**Срок срабатывания — 2 ноября 2026 года.** В этот день образ `macos-14` снимается с поддержки GitHub Actions. К этой дате `MACOSX_DEPLOYMENT_TARGET` в `project.yml`, матрица в `.github/workflows/build.yml`, требования в `README` и это место в `SPEC` переводятся на минимум, для которого образ ещё есть, — сегодня это 15. Отдельного решения тогда принимать не нужно, оно принято сейчас.

Обратное действие правила тоже в силе: понизить заявленный минимум можно только вместе с добавлением образа, на котором он проверяется.

Язык: Swift 6, строгий режим конкурентности.

### 5.0 Сборку можно спросить, из какого она коммита

В «Подробностях» первая строка — «Это приложение»: версия, а у релиза ещё и короткий коммит. Первая, потому что все остальные строки про то, на что приложение смотрит, а эта про то, чем смотрят.

**Одного номера версии для этого не хватает.** `MARKETING_VERSION` меняют раз в релиз, поэтому все сборки между двумя релизами носят один и тот же номер и содержат разный код. Коммит подставляется в `CCWidgetCommit` скриптом `Scripts/release.sh` и пуст во всякой другой сборке — тогда строка так и говорит, «не релизная сборка», а не оставляет пустое место, которое читалось бы как релиз с потерянным штампом.

**Замерено, а не предположено:** обычная сборка оставляет ключ в plist с пустым значением, сборка с `CCWIDGET_COMMIT=deadbee` — со значением `deadbee`. Значит проверка «коммита нет» — это проверка на пустоту, а третий вариант, `unknown`, принадлежит бандлу с вырезанными ключами, а не какой-либо сборке этого проекта. Все три производит `AppBuildTests`.

**Зачем заведено.** 17 августа 2026 установленный бандл сообщал `0.3.2`, содержа работу, которой в теге `v0.3.2` нет: вопрос «ту ли сборку я запускаю» пришлось решать `strings` по двоичному файлу и датой правки исполняемого. Дважды за один день. Отчёт, начинающийся словами «экспортёр говорит», стоит меньше отчёта, который начинается с того, чем он снят.

### 5.1 Переустановка при разработке

Ставить сборку следует через `Scripts/reinstall.sh`, а не руками. Последний шаг скрипта — **`killall chronod`, и он обязателен.**

Демон виджетов держит расширение загруженным и переживает подмену бандла: после копирования новой сборки он продолжает исполнять прежний код. **`chronod` Apple не документирует вовсе** — всё в этом разделе получено на живой системе и держится на наблюдении, а не на источнике. Правки при этом выглядят неприменившимися — виджет рисует старое, логи содержат сообщения, которых в новых исходниках уже нет. Проверено на живой системе: расширение успевает подняться из наполовину скопированного бандла и потом крутит его до перезапуска демона.

`chronod` перезапускается системой сам через секунды, все виджеты перерисовываются. Отдельно отметим: перезагрузка таймлайнов из приложения (`reloadAllTimelines()`) эту проблему **не** решает — она заставляет старый код построить новый таймлайн, но кодом он остаётся старым.

Порядок в скрипте важен: остановить процессы → подменить бандл → запустить приложение (регистрирует расширение) → перезапустить демон.

**Падение расширения выглядит как устаревшие данные, а не как падение.** Это главное, что стоит знать при разборе: система показывает последний кадр, который успел отрисоваться, и на столе это неотличимо от «снимок не обновляется». 7 августа 2026 расширение падало на каждой отрисовке пять часов подряд — двадцать восемь отчётов за день, первый через две секунды после установки, — и обе стороны искали дефект в данных и в вёрстке.

Порядок разбора:

```sh
# 1. Были ли падения после установки текущей сборки.
./Scripts/check-widget-health.sh

# 2. Если да — самый ранний отчёт ближе всего к причине; поздние часто следствие.
ls -1 ~/Library/Logs/DiagnosticReports/CCWidgetExtension-*.ips | head
```

Две ловушки, обе стоили времени:

- **`log show` без `--info` показывает пустоту**, потому что весь лог провайдера идёт этим уровнем. Пустой вывод не означает, что расширение молчит.
- **Строка «timeline built» не доказывает, что отрисовка завершилась.** Она пишется в начале работы; падение случается позже, при размещении видов. В тот день вывод «провайдер строил таймлайн, значит расширение живо» был сделан именно так и оказался неверным — в ту же секунду лежал отчёт о падении.
- **macOS переписывает `mtime` старых `.ips`**: отчёт, рождённый в 16:10, имел `mtime` 16:39. Сравнивать надо время из имени файла, а не `-newer`.

**Чего не увидит ни одна из проверок в `Tests/`.** Все они исполняются в тестовом процессе, где нет WidgetKit. В тот день 221 проверка была зелёной, и восемьдесят один рендер через `ImageRenderer` — все виды, все состояния, три языка — прошёл чисто, тогда как плитка падала каждый раз. WidgetKit архивирует состояния вида (`_ArchivedViewHost.archiveStates` в стеке) с предложениями размеров, которых не делает ни один инструмент рендеров.

**Практический вывод, вошедший в код:** `GeometryReader` в ряду виджета не используется. Шкала рисуется капсулой, сжатой `scaleEffect` от левого края, — геометрия не читается, и предложение, на котором можно споткнуться, не возникает. `ForecastChart` его ещё использует; это известный риск того же класса, пока не проявлявшийся.

**Иконку система кэширует, и «не изменилось» обычно значит «кэш».** Приложение пересобрано, `.icns` в бандле новый, а Dock, Finder и Spotlight показывают прежнюю картинку — это не провал сборки. Порядок проверки, от дешёвого к дорогому:

```sh
# 1. Убедиться, что новая иконка вообще в бандле — это отделяет сборку от кэша.
sips -s format png --resampleWidth 256 \
     /Applications/CCWidget.app/Contents/Resources/CCWidget.icns --out /tmp/icon.png && open /tmp/icon.png

# 2. Тронуть бандл и перезапустить оболочку: этого хватает почти всегда.
touch /Applications/CCWidget.app
killall Dock
killall Finder
```

Если и после этого стоит старая — остаётся общесистемное хранилище
`/Library/Caches/com.apple.iconservices.store`, для очистки которого нужен `sudo`; в этом проекте до него не доходило ни разу, и вслепую его чистить не следует.

**Проверять надо на местах, а не рендером.** Инструмент рендеров рисует виды сам и о системных эффектах ничего не знает: скруглением, тенью и бликом иконку наделяет система. Что смотреть — Dock, Finder, галерея виджетов, Spotlight, и обе темы.

**Галерея виджетов держит иконку отдельно от Dock, Finder и Spotlight.** Наблюдалось 7 августа 2026: после замены иконки три первых поверхности показали новую сразу после `killall Dock` и `killall Finder`, а галерея — прежнюю, и `killall chronod` её не сдвинул.

**Чью иконку показывает галерея.** Приложения-контейнера, и иной быть не может: у `CCWidgetExtension.appex` нет ни `.icns`, ни `Assets.car` — проверено в собранном бандле. Требование Apple прямое: «An extension's icon must be the same as the app icon of its containing app» (App Extension Programming Guide, «Creating an App Extension»). Оговорка: документ архивный, под macOS 26 не обновлялся, и это единственное место, где утверждение сформулировано, — см. `SOURCES.md`. Отдельного артефакта иконки у расширения нет, заводить его не нужно и, по этому же требованию, нельзя.

**Порядок сброса. Документации на него нет** — Apple описывает, как иконка попадает в бандл, и не описывает, чем очищается кэш галереи. Ниже собрано из документированных фактов и одного наблюдения; порядок от дешёвого к дорогому:

```sh
# 1. Переустановить бандл и запустить приложение хотя бы раз. Это
#    документировано: виджет появляется в галерее только после того, как
#    контейнер был запущен после установки (apple/widgetkit-creating-a-widget-extension.md).
./Scripts/reinstall.sh

# 2. Перерегистрировать расширение в базе PlugInKit. Флаг документирован в
#    `man pluginkit`: «Explicitly adds plugins at the file location(s) given».
#    Проверяемо: `pluginkit -m -v -p com.apple.widgetkit-extension` печатает
#    UUID записи и дату — после -a меняются оба.
pluginkit -a /Applications/CCWidget.app/Contents/PlugIns/CCWidgetExtension.appex
pluginkit -m -v -p com.apple.widgetkit-extension | grep ccwidget

# 3. Перезапустить демон виджетов. Не документировано, наблюдение проекта.
killall chronod
```

**Что из этого проверено, 7 августа 2026.** Шаги 1–3 выполнены на машине владельца: бандл переустановлен, приложение запущено, регистрация в PlugInKit обновлена (UUID и дата сменились, наблюдалось), демон перезапущен. **Галерея всё равно показала прежнюю иконку.**

Шаг 4 — выход из учётной записи и вход обратно — **не выполнялся, и это решение, а не незавершённость.** Вопрос, ради которого он затевался, дешевле и вернее отвечается на чистой учётной записи: старая иконка простояла на этой машине месяцами, и то, что здесь выглядит как неподатливый кэш, у человека с установкой с нуля может не существовать вовсе. Гонять сессионные кэши, чтобы выяснить свойство одной машины, — не та цена.

Поэтому вопрос передан в `Docs/container-permission-test.md`: там, где проверка и так идёт на новой учётной записи, добавлен пункт про иконку в галерее. Оба его исхода значимы, и оба записаны в самом документе.

**Проверять галерею придётся глазами.** Программно она не открывается: `System Events` отвечает на запросы о процессах, но имён элементов Dock и Центра уведомлений не отдаёт, а нажатия клавиш до системы не доходят. Открывается вручную — правый клик по рабочему столу, «Изменить виджеты».

#### Последняя запись сессии выбрасывалась

**Дефект, найденный замером фоновой работы 17 августа.** Наблюдатель рационировал перезагрузки минутным окном и внутри этого окна изменение **выбрасывал**, а не откладывал. Обоснование в коде: «следующая запись экспортёра нас разбудит». Оно верно, пока человек работает, и неверно ровно тогда, когда важно: у последней записи сессии нет следующей.

То есть: работа закончена, пришёл последний снимок, он попал в минутное окно — и плитка остаётся с предыдущим до тех пор, пока WidgetKit не придёт сам, до получаса. Именно в момент, когда человек закрывает терминал и смотрит на виджет.

Замерено до починки: одна запись внутри окна, затем три с половиной минуты неизменной плитки при работающем в фоне приложении.

**Что сделано.** Изменение внутри окна теперь откладывается: наблюдатель запоминает, что перезагрузка должна произойти, и возвращается за ней, когда окно закроется. Пачка записей внутри одного окна должна одну перезагрузку, а не по одной на запись — иначе починка тратила бы тот самый бюджет, ради которого окно и существует. Остановка наблюдателя отменяет отложенное: закрывающееся окно или выходящее приложение не перезагружают виджет по пути наружу.

**Отложенное выполнение внедряется, как и часы.** Проверке нельзя ждать пятьдесят пять настоящих секунд — это надежда, а не проверка. Живой наблюдатель спит, проверка держит отложенное у себя и запускает когда решит, а заодно утверждает **на сколько** отложили: на остаток окна, а не на всё окно.

#### Регистрации расширения копятся от каждой сборки, и их надо снимать

**Наблюдение 7 августа 2026: в базе PlugInKit лежало пятнадцать записей одного и того же `dev.illvminat.ccwidget.widget`.** Пути — все существующие, ни одной мёртвой: `DerivedData` от сборок Xcode и от прогонов проверок, `.build` рабочего дерева, `.build` временных деревьев прошлых сеансов, и копия ещё от `ccgauge` — проекта, переименованного 31 июля.

Причина простая и постоянная: расширение регистрируется из того каталога, где собрано, а собирается оно при каждой установке и при каждом прогоне проверок. За день активной разработки записей набирается десяток.

**Обычная команда их не показывает.** `pluginkit -m -v -p com.apple.widgetkit-extension` печатает одну запись — ту, что система считает действующей. Весь список отдаёт только

```sh
pluginkit -m -A -D -vvv -p com.apple.widgetkit-extension | grep -c 'dev.illvminat.ccwidget.widget'
```

Признак беспорядка виден и со стороны демона: в журнале `chronod` при запуске идёт подряд четырнадцать строк `Updated extension: <WidgetExtension - identifier: dev.illvminat.ccwidget…>, now with pluginUUID …`, каждая с новым UUID и одним и тем же прежним. После уборки строка одна — `Unchanged extension`.

**Снимаются по пути бандла:**

```sh
pluginkit -r /path/to/CCWidget.app/Contents/PlugIns/CCWidgetExtension.appex
```

Оставлять следует одну — `/Applications/CCWidget.app/…`, ту, что ставит `reinstall.sh`. Уборка обратима: следующая сборка зарегистрирует свой путь снова.

**Чего уборка не чинит.** Ни падений, ни пустой плитки: оба дефекта 7 августа воспроизводились и при одной регистрации. Опыт, поставленный до уборки, ею обесценивается — сравнение двух сборок при пятнадцати записях в базе не даёт вывода ни о какой из них, и один такой опыт в этот день пришлось признать негодным и повторить.

#### Что сдвинулось и что нет: галерея держит три разных кэша

Вечером 7 августа 2026 из базы PlugInKit были сняты четырнадцать лишних регистраций расширения (`pluginkit -r`, причины — ниже в этом же разделе). После этого галерея показала:

| Что | Состояние | Откуда берётся |
|---|---|---|
| Название виджета | **Обновилось** | `CFBundleName` контейнера, через запись PlugInKit |
| Описание | **Обновилось** | `.description(_:)` из `WidgetConfiguration` |
| Три предпросмотра | **Рисуются**, все размеры | таймлайн расширения, свежие данные |
| Иконка | **Осталась прежней** | кэш иконок системы, к записи расширения не привязанный |
| Имя окна виджета в Центре уведомлений | **Осталось прежним** — «Gauge for Claude Code» | снимок метаданных на момент добавления экземпляра |

**Почему они разошлись.** Первые три система перечитывает из записи расширения: снятие лишних регистраций заставило её перечитать запись, и всё, что в ней, обновилось разом. Иконка в записи не хранится — она хранится там же, где иконки приложений вообще, и переустановка бандла, `pluginkit -a` и `killall chronod` её не трогают; на этой машине она пережила и то, и другое, и третье. Имя экземпляра в Центре уведомлений — третий случай: оно снято в момент, когда виджет туда добавили, и не следует за переименованием вовсе, что и видно по слову «Gauge», которого в проекте нет с момента переименования.

**Дальше не гонимся.** Ответ про иконку даёт чистая учётная запись — см. пункт про неё выше и `Docs/container-permission-test.md`. Здесь важно другое: **обновление одного из этих трёх ничего не говорит об остальных двух.** Проверяя, доехала ли правка до пользователя, называть надо конкретную поверхность, а не «галерею» целиком.

Побочная польза для отладки: старое имя в окне Центра уведомлений — не помеха, а опора. `Scripts/tile-probe.swift` ищет окно по подстроке «Claude Code», которая пережила переименование; см. 9.3.

**Записи уровня `.info` система в журнале не хранит, и `log show` без флага
`--info` выглядит как «расширение не вызывается».** Весь лог провайдера
(`ccwidgetWidgetLog.info`) идёт этим уровнем. Пустой вывод

```sh
log show --last 24h --predicate 'subsystem == "dev.illvminat.ccwidget"'
```

означает не молчание расширения, а то, что уровень не запрошен. Правильно:

```sh
log show --info --last 2h --predicate 'subsystem == "dev.illvminat.ccwidget"'
log stream --level info --predicate 'subsystem == "dev.illvminat.ccwidget"'
```

Ошибка стоила получаса при замере размеров из раздела 9: провайдер работал,
виджеты стояли на столе, а журнал по всем признакам говорил, что расширение
не поднималось ни разу за сутки. Проверять надо через `--info`, прежде чем
делать вывод, что виджета на столе нет.

### 5.1.1 Как посмотреть состояние по возрасту, не дожидаясь его

Пороги свежести — час и сутки — иначе не увидишь: ждать сутки ради одной ветки нельзя, а править `capturedAt` в снимке наивно не выходит. Экспортёр перезаписывает снимок на **каждую** перерисовку статуслайна, то есть десятки раз в минуту, и состаренный файл живёт секунды. Гонка с ним — дело случая; в неё легко поверить, что ветка не работает.

Порядок, который работает без гонки:

```sh
EX=~/Library/Containers/dev.illvminat.ccwidget.widget/Data/Library/Application\ Support/ccwidget
cp "$EX/snapshot.json" /tmp/snap.real          # вернуть потом
osascript -e 'tell application "CCWidget" to quit'
# состарить capturedAt на нужную величину, например на 25 часов
chmod 500 "$EX"                                 # экспортёр больше не запишет
killall chronod; open /Applications/CCWidget.app
# смотреть и снимать
chmod 700 "$EX"; cp /tmp/snap.real "$EX/snapshot.json"; killall chronod
```

Что здесь зачем. Приложение гасится, чтобы наблюдатель не перезагружал виджет по своему усмотрению и не упирался в минутный ограничитель. Каталог закрывается на запись, чтобы экспортёр не вернул настоящий момент: его запись просто не проходит, а след пропуска (раздел 3) записаться тоже не сможет и будет молча пропущен — это единственное место, где тишина заложена намеренно. `killall chronod` заставляет демон перечитать снимок немедленно, а не ждать своей получасовой политики.

Так были увидены обе ветки — часовая и суточная — сразу на всех поверхностях.

### 5.2 Пути пользователя приходят параметром

**Правило: код, работающий с путями в домашнем каталоге пользователя, обязан принимать корень как параметр.** Вычислять его внутри себя запрещено.

Правило появилось после двух ошибок подряд, обе из-за `homeDirectoryForCurrentUser`. Сначала он вернул контейнер вместо настоящего дома, и путь обмена удвоился (раздел 2.2). Затем он проигнорировал переменную `HOME`, из-за чего попытка проверить установщик в подставном каталоге отработала по настоящему конфигу и переписала живой `settings.json`.

Второй случай важнее первого. Установщик, который сам решает, где дом, **невозможно проверить, не тронув чужие файлы**, — а установщик правит конфигурацию Claude Code и обязан быть покрыт проверками плотнее всего остального.

Как это выглядит: `Installer` — структура с полями `home`, `exchangeDirectory` и `templateURL`; боевые значения собирает `Installer.live()`. `SnapshotStore` даёт пару `exchangeURL(home:)` и `widgetContainerExists(home:)` рядом с беспараметрическими версиями. Проверки в `Tests/` работают во временном каталоге и настоящего `~/.claude` не касаются.

**Правило шире путей: внедряется любая зависимость, а не переключается флаг.** Окно приложения сначала получило булев `isSample` и второй инициализатор, чтобы рисоваться для снимков экрана в заданном состоянии. Это тот же дефект в другом обличье: тип сам решает, как себя вести, и его поведение нельзя задать снаружи, не изменив его код.

Правильно — источник состояния параметром. `StatusView` принимает `StatusModel`: боевая читает диск и держит наблюдателя, `FixedStatusModel` отдаёт заданное и ничего не запускает. Внутри окна нет ни одной ветки «а если это снимок экрана», а состояния, которые иначе пришлось бы воспроизводить руками — подменённый экспортёр, отсутствующая настройка, ожидание данных, — снимаются одной командой.

Признак, по которому дефект узнаётся: если в типе появляется поле, единственное назначение которого — отличить тест от боевого запуска, зависимость внедрена не полностью.

Исключение единственное: внутри песочницы дом процесса **и есть** его контейнер, и `NSHomeDirectory()` там не источник ошибок, а единственно верный ответ.

## 6. Модели данных

```swift
struct Snapshot: Codable, Sendable {
    let schemaVersion: Int
    let capturedAt: Date
    let sessionId: String?
    let claudeCodeVersion: String?
    let model: ModelInfo?
    let project: ProjectInfo?
    let limits: Limits
    let context: ContextInfo?
    let cost: CostInfo?
}

struct Limits: Codable, Sendable {
    let fiveHour: LimitWindow?
    let sevenDay: LimitWindow?
}

struct LimitWindow: Codable, Sendable {
    let usedPercentage: Int
    let resetsAt: Date

    var remainingPercentage: Int { 100 - usedPercentage }
}
```

`capturedAt` и `resetsAt` декодируются из unix-времени через `.secondsSince1970` в `JSONDecoder.dateDecodingStrategy`.

**Почему `LimitWindow`, а не `Window`.** Короткое имя сталкивается со сценой `SwiftUI.Window` и требует полного имени в каждом файле с интерфейсом. Приставка снимает конфликт раз и навсегда.

**Все поля кроме `schemaVersion`, `capturedAt` и `limits` опциональны.** Это не перестраховка: `rate_limits` реально отсутствует в первые секунды сессии.

**Разбор `Limits` мягкий и это норма.** Поля внутри `LimitWindow` объявлены обязательными, но `resets_at` может прийти `null` — тогда строгий разбор уронил бы весь снимок из-за одного испорченного окна. Поэтому `Limits` имеет собственный `init(from:)`, где каждое окно разбирается через `try?`:

```swift
public init(from decoder: Decoder) throws {
    let c = try decoder.container(keyedBy: CodingKeys.self)
    fiveHour = c.decodeSoft(LimitWindow.self, forKey: .fiveHour,
                            path: "limits.fiveHour", decoder: decoder)
    sevenDay = c.decodeSoft(LimitWindow.self, forKey: .sevenDay,
                            path: "limits.sevenDay", decoder: decoder)
}
```

`decodeSoft` — не просто `try?`: он пишет отброшенное поле в лог и в диагностику снимка. Голый `try?` здесь был бы прямым нарушением правила 6.1 ниже.

Битое окно даёт `nil` и рисуется прочерком, соседнее окно и весь остальной снимок выживают. Это то же требование мягкого разбора, что и в разделе 14, применённое на уровне модели.

### 6.1 Мягкий разбор обязан быть громким

**Правило: молчаливое проглатывание запрещено.** Каждое срабатывание `try?` при разборе сопровождается двумя записями — в системный лог и в диагностику снимка. Мягкий разбор без этого превращается в тихую потерю данных: поле исчезает, виджет рисует прочерк, и настоящая причина ищется вслепую.

Правило появилось не из принципа. Живой снимок принёс дробный процент (раздел 2.1), мягкий разбор отработал как задумано и отбросил всё пятичасовое окно целиком. Виджет показал прочерк при исправных данных, и на поиск причины ушло время, которого одна строка в логе стоила бы дешевле.

**Три обязательных места:**

1. **Лог.** `os.Logger`, подсистема `dev.illvminat.ccwidget`, категория `parsing`, уровень `error`. В сообщении — имя поля, сырое значение из JSON и причина отказа. Сырое значение снимается отдельным разбором в `JSONValue`: без него в логе остаётся «поле не разобралось», что бесполезно.
2. **Поле `diagnostics` в `Snapshot`.** Список `ParseIssue` — поле, сырое значение, причина. В норме пустой. Собирается при декодировании через `DiagnosticsCollector` в `userInfo` декодера и в JSON не хранится: это свойство разбора, а не данных.
3. **Окно приложения.** Если список непуст, показывается блок с перечнем отброшенных полей. Единственное место, где разработчик увидит проблему, не открывая Console.app.

Единственное исключение — отсутствующее поле. `rate_limits` в первые секунды сессии нет штатно, и шуметь об этом не надо. Отличие принципиальное: **нет поля — молчим, поле есть и не разобралось — кричим.**

## 7. Прогноз

Единственная функция, которой нет ни у одного конкурента. Ей стоит уделить время.

**Вход:** `history.jsonl`, отфильтрованный по текущему недельному окну (записи, у которых `resetsAt` совпадает с актуальным).

**Алгоритм:**

1. Отбросить записи старше текущего окна — при сбросе процент падает скачком, и регрессия по смешанным окнам даст мусор.
2. Отбраковка. Порогов четыре, и каждый отвечает за свою ошибку:

   | Порог | Значение | От чего защищает |
   |---|---|---|
   | Точек | не меньше 10 | При дедупликации раз в 10 минут это значит, что точки не из одной вспышки активности |
   | База наблюдений | не меньше 2 часов | Полчаса давали экстраполяцию в **триста раз** дальше базы |
   | R² взвешенной регрессии | не меньше 0,7 чтобы начать показывать, не меньше 0,58 чтобы продолжать | Ниже линия не описывает данные, и уверенная дата вводит в заблуждение сильнее прочерка. Два порога, а не один — см. «Ворота R² с гистерезисом» ниже |
   | Горизонт | не дальше 10 длин базы | Два часа наблюдений дают право говорить о двадцати часах, не о неделе |

   R² берётся из тех же сумм, что уже считаются, — нужен один дополнительный проход. Доверительный интервал по наклону был бы честнее, но требует предположения о нормальности остатков, которого у нас нет.

   **Плато определяется по целым процентам, а не по дисперсии.** При одинаковых значениях средневзвешенное выходит на волос мимо, дисперсия получается микроскопически положительной, наклон — микроскопически ненулевым, и плато уезжало в «данных мало». Проверено на стенде.
3. Линейная регрессия методом наименьших квадратов: `usedPercentage` от времени.
4. Если наклон не положительный — расход стоит, прогноза нет.
5. Экстраполировать до 100%, получить момент `t₁₀₀`.
6. Сравнить с `resetsAt` — но только в пределах горизонта:
   - исчерпание ближе десяти длин базы → красный пунктир и подпись с датой под тильдой
   - исчерпание дальше горизонта, а сброс ближе → жёлтая линия, «хватит до сброса»
   - и то и другое за горизонтом → **темп без даты**

**Горизонт считается по эффективному охвату весов, а не по полному размаху точек.** Наклон приходит из регрессии с периодом полураспада 12 часов; девять десятых веса лежат в последних часах, и ограничитель обязан мерить ту же величину. Пока он мерил полный размах, тридцать часов точек давали горизонт в 298 часов при одиннадцати часах реальных наблюдений — на живых данных это дало красную дату «кончится в четверг» при 12 % израсходованного на неделе, дошедшей до 14 %. Замер по 118 часам настоящей истории: до починки ложная дата показывалась 58,8 % времени, после — ноль. Разбор и числа — `Docs/estimate-review.md`.

**Ограничение горизонта распространяется и на «хватит до сброса».** Это утверждение о будущем ровно в той же мере, что и дата исчерпания, и подкреплено оно должно быть так же.

### Ворота R² с гистерезисом

У порога R² два значения, а не одно: **0,7 чтобы начать показывать вердикт и 0,58 чтобы продолжать его показывать**. Между ними вердикт держится тем, что он уже на экране.

Причина — замер. На 118 часах настоящей истории медиана R² равна 0,71 при пороге 0,7, то есть показатель живёт ровно на границе: блок включался и выключался восемь раз за пять суток, один раз — на одну минуту. Обе стороны такого мерцания истинны, ни одна не тревожит, но картинка, меняющаяся сама по себе, читается как поломка.

**Откуда 0,58.** За те же 118 часов R² уходил ниже 0,7 при показанном вердикте четыре раза. Две просадки достигали 0,648 и 0,653 и возвращались через минуту и через полтора часа — в неделе ничего не менялось, дрожал сам показатель. Самая глубокая, 0,507, пришла после разрыва в истории на 67 часов и не вернулась: линия действительно перестала что-либо описывать, и убрать вердикт там было правильно. Порог выхода обязан лежать ниже 0,653 и выше 0,507; 0,58 — середина этого промежутка, то есть максимально далеко от обеих ошибок, какое даёт одна история. Запас в обе стороны, 0,073, составляет примерно восемь десятых стандартной ошибки R² в этой рабочей точке (0,089 при медианном эффективном размере выборки 32). Больше точности из одной истории не выжать, и лишние знаки после запятой были бы выдумкой.

**Порог входа не менялся и меняться не должен.** Всё, что обосновывало 0,7, обосновывало именно вход. Замер на профилях подтверждает цену подъёма: на профиле «тихо, потом всплеск» вход 0,78 отнимает часть предупреждения, 0,86 отнимает его целиком. Асимметрия ворот достигается тем, что выход отпущен, а не тем, что вход поджат, — и это единственное направление, которое не может стоить ни одного часа предупреждения.

**Состояние ворот не хранится, а восстанавливается.** Гистерезис требует знать, что было на экране мгновение назад. Запоминать это значило бы, что виджет пишет состояние, — он только читает, — и что вердикт зависит от того, когда система разбудила провайдер. Поэтому ворота проигрываются заново по префиксам истории текущего окна: вердикт становится функцией файла и ничего больше, один и тот же файл даёт один и тот же ответ на любой машине и при любом обновлении. Цена — по одной подгонке на точку: 1,8 мс на 200 точках, 26 мс на 1000, 98 мс на пределе усечения в 2000 строк, один раз на построение таймлайна.

Префикс, который не даёт R² вообще — меньше десяти точек, база короче двух часов, плато, — оставляет ворота как есть. Это не свидетельство ни за, ни против; считать «расход остановился» за «линия перестала описывать данные» значило бы впустить мерцание через другую дверь.

**Замер, ради которого всё делалось.** На тех же 118 часах: восемь переключений состояния становятся пятью, и уходят ровно те три, что были мерцанием. Оставшиеся пять — первое появление вердикта, недельный сброс, повторный вход после сброса, переход «хватит до сброса» → «темп без даты» по горизонту и снятие вердикта при R² = 0,507. Каждое отвечает чему-то, что действительно произошло. Ложных дат по-прежнему ноль. Числа воспроизводятся `./.build/ccwidget-replay <путь к history.jsonl>`, разбор — `Docs/estimate-review.md`.

**Время предупреждения не пострадало и не должно.** Четыре синтетических профиля, которые исчерпывают квоту, прогнаны с гистерезисом и без него: 118,83 / 48,33 / 4,67 / 114,15 часа предупреждения в обоих случаях, до отсчёта. Это следствие неподвижного порога входа, и оно закреплено проверкой: ворота обязаны пропускать вердикт всегда, когда R² не ниже порога входа.

Само значение порога входа закреплено не ею — она написана через ту же константу и поедет вместе с ней, — а записанными временами предупреждения. Подъём входа до 0,80 отнимает у профиля «тихо, потом всплеск» предупреждение с 4,67 часа до 3,83, и проверка падает; проверено подъёмом, а не предположено. Устойчивость картинки не стоит ни одного часа предупреждения — если когда-нибудь встанет такой выбор, выбирается предупреждение.

Чего не закрывает ни одна из двух проверок — слишком низкий порог выхода. На настоящей истории это видно сразу: ниже 0,52 число переключений снова растёт, потому что вердикт удерживается при подгонке, которая действительно умерла. Синтетические недели так низко R² не опускают, и набор этого не заметит. Проверка здесь — `ccwidget-replay` на живой истории.

### Три состояния вместо двух

Из ограничения горизонта следует неприятное: сразу после сброса недели до конца окна почти семь суток, и чтобы горизонт до них дотянулся, нужна база в семнадцать часов. Всё это время строгий алгоритм показывал бы прочерк, а пользователь решил бы, что функция сломана.

Поэтому состояний три, а не два:

| Состояние | Что показываем | Почему так честно |
|---|---|---|
| Данных мало | ничего | Меньше десяти точек, база меньше двух часов, R² ни разу не поднялся до порога входа или упал ниже порога выхода |
| **Темп без даты** | «~0,7 %/час» | Скорость — **измерение**, а не экстраполяция, и верна при любой длине базы. Даты нет, пунктир не рисуется: линия до ста процентов и есть та самая неназванная дата, только нарисованная |
| Темп с датой | «~0,7 %/час» и «Runs out ~Чт 07:00» | Горизонт дотянулся |

Разделение принципиальное: у измерения и у экстраполяции разная цена ошибки, и смешивать их в одном прочерке неправильно.

### Слова в интерфейсе

Блок называется **Estimate**, а не Forecast. Дата пишется под тильдой — «Runs out ~Чт 07:00». Под подписью мелким стоит длина базы — «based on 4 hr of data»: без неё «~Чт 07:00» выглядит одинаково уверенно и на двух часах истории, и на трёх днях. Слово «prediction» не употребляется нигде.

**Дедупликация при записи.** Статуслайн перерисовывается на каждый чих — замеры дали пятнадцать вызовов за две с половиной минуты, все с одним и тем же процентом. Писать каждый вызов бессмысленно: порог усечения пробивается за пару часов работы, а полезных точек в файле не прибавляется.

Правило: новая строка пишется, только если выполнено хотя бы одно условие —

- `sevenDay.usedPercentage` отличается от последней записи;
- с момента последней записи прошло более 10 минут;
- последней записи нет либо у неё другой `resetsAt` (сменилось окно).

Десятиминутная отсечка нужна, чтобы регрессия видела ровное плато, а не разрыв: без неё период простоя выглядел бы как отсутствие данных, а не как нулевой расход.

**Снимок не пишется, если в вызове нет лимитов.** Первая отрисовка статуслайна в новой сессии приходит без ключа `rate_limits` вовсе и с `context_window.used_percentage` равным `null` — проверено на записи настоящего статуслайна, две таких строки из двадцати девяти. Экспортёр перезаписывал снимок на каждый вызов, поэтому перезапуск Claude Code обнулял виджет: цифры, на которые человек смотрел, заменялись пустотой до первого запроса новой сессии.

Вызов без `rate_limits` не сообщает, что лимиты равны нулю. Он сообщает, что эта отрисовка о них ничего не знает, а это не новость. Снимок на диске остаётся, его возраст продолжает расти, и возраст — то самое, что честно говорит о свежести. Первый же запрос сессии приносит настоящие числа.

Ничего не сливается и не сохраняется вручную: запись просто пропускается. Старые числа под свежим `capturedAt` были бы хуже обоих вариантов — это ложь о возрасте.

**Пропуск не молчит.** Правило про запрет тихих запасных путей действует и здесь, и не ради отладки начала сессии — там пропуск ожидаем и длится секунды. Ради случая, которого никто не видел: если `rate_limits` однажды пропадёт посреди сессии и не вернётся, экспортёр замолчит навсегда, снимок будет стареть, и симптом станет неотличим от «Claude Code не запущен».

Поэтому рядом со снимком появляется `export-skipped.json`: когда молчание началось, почему и в какой сессии. Файл пишется **на входе в молчание, а не на каждую отрисовку** — статуслайн перерисовывается десятками раз в минуту, а ценна не частота наблюдения, а момент начала; повторные пропуски его не перезаписывают. Первая же удачная запись снимка файл удаляет. `ccwidget-dump` печатает его первым делом, до всего остального, потому что он меняет смысл старого снимка: экспортёр работает и решает не писать, а не отсутствует.

*Может ли поле пропасть после того, как появилось.* На записи настоящего статуслайна — 29 вызовов, три сессии — не пропадало ни разу: `rate_limits` отсутствует ровно в первом вызове каждой сессии и присутствует во всех последующих. Это наблюдение, а не гарантия: двадцать девять вызовов ничего не говорят о поведении при недоступном сервисе, при аккаунте без лимитов и при следующей смене формата. Ради этого незнания след и заведён.

**Отдельного состояния окна для этого нет, и это решение.** Показать человеку «экспортёр молчит» окно сегодня не умеет: на экране устойчивое молчание неотличимо от закрытого Claude Code. Заводить ради этого состояние вида, ветку и строку в шести языках — значит покрывать сценарий, которого никто не наблюдал, а вариант, которого никто не производит, ошибочен вечно по построению. Пока след виден в `ccwidget-dump`, а `README` ведёт к нему того, кто пришёл с неполадкой.

**Признак, по которому решение пересматривается.** Он назван здесь именно для того, чтобы его можно было узнать при встрече:

> `export-skipped.json` существует дольше минуты подряд при работающем Claude Code.

Минута, а не секунды: пропуск в начале сессии живёт ровно до первого запроса, то есть секунды. Файл, переживший минуту работающего Claude Code, — это уже не начало сессии, а тот самый устойчивый пропуск.

Если такое встретится в жизни хотя бы раз — сценарий перестаёт быть неподтверждённым, и окно получает отдельное состояние: «статуслайн работает, но лимитов не присылает», со своей строкой и своим объяснением. До тех пор — не заводить.

**Усечение истории:** держать не более 2000 строк, при превышении переписывать файл, оставляя последние 1000. Иначе за месяц файл вырастет до неприличного размера, а виджет обязан читать его быстро.

**Сглаживание:** взвешивать точки по свежести (экспоненциально), чтобы вчерашний марафон не портил сегодняшний прогноз.

## 8. Пороги и цвета

```swift
enum Level { case healthy, warning, critical, depleted }
```

### Свежесть и закрывшееся окно — разные оси

**Свежесть отвечает «давно ли мы смотрели», закрытое окно — «действует ли ещё то, на что мы смотрели».** Это независимые вопросы, и путать их дорого. Снимок секундной давности может нести пятичасовое окно, закрывающееся через секунду; ещё через секунду окно закрыто, а снимку по-прежнему две секунды. Возраст не изменился, действительность данных изменилась.

Различение шире этого случая: возраст наблюдения — свойство того, когда мы посмотрели, а закрытое окно — свойство того, на что мы смотрели. Строке для второго вопроса не нужно ничего сверх того, что у неё уже есть: `resetsAt` лежит на самой `LimitWindow`, и сравнение с текущим моментом не заводит второго понятия свежести.

**Почему по строкам, а не по снимку.** Строки стареют неодинаково. Недельный процент двенадцатичасовой давности примерно верен; пятичасовой описывает окно, закрывшееся дважды. Приглушение всего снимка красит обе одинаково и тем самым утверждает, что они устарели в равной мере — а это неправда, и видна она в самый частый момент взгляда на виджет: утром, при возвращении к машине.

**Что показывает строка с закрывшимся окном.** Цифр нет — прочерк, пустая шкала, нейтральный глиф; справа стоит «сброшено». Это то же решение, что принято на сутках: число 19 % — факт о законченном окне, а текущее неизвестно, и прочерк отвечает на заданный вопрос честно. Большой виджет сохраняет момент — «сброс Вт 00:30 · сброшено»: когда закончилось, знать полезно; чего нельзя — называть отсчёт до него, который упирается в ноль и читается как «вот-вот сбросится».

Слово выбрано коротким по замеру, а не по вкусу: слот подписи на средней плитке — 66 пунктов, и «окно закрылось» требует 82, «Fenster beendet» — 81, тогда как «сброшено» укладывается в 52, «beendet» в 41. Двумя словами по-русски не выходит и иначе: «период истёк» требует 69.

**По-русски было «закрылось», и это слово вводило в заблуждение.** 17 августа 2026 владелец закрыл окно IDE, увидел на плитке «Использовано за 5 часов — закрылось» и связал одно с другим. Совпадение было случайным — пятичасовое окно сбросилось в 18:30, — но прочтение закономерно: на экране «окно» это окно программы, и «закрылось» относят к нему, а не к периоду лимита. Замена на «сброшено» убирает столкновение и говорит словарём остального интерфейса, где неделя «сбрасывается» в четверг.

Английское `closed` и переводы на немецкий, японский и китайский оставлены: три из них и так говорят «закончилось», а не «закрылось», и ни одного наблюдения о неверном прочтении по ним нет. Испанское `cerrada` — тот же класс, что бывшее русское, но менять его по аналогии значит угадывать за носителя; помечено здесь и ждёт наблюдения.

**Вслух строка говорит «сброшено», а не «нет данных».** Это разные утверждения: данные пришли, они про законченный период. Слушателю, которому сказали «нет данных», останется искать неисправность, которой нет.

**Мигание на границе принято.** При активной работе на каждой пятичасовой границе строка на секунды уходит в «сброшено», пока не придёт следующий снимок с новым окном. Это честно: окно действительно закрылось, а нового мы ещё не видели. При простое строка остаётся закрытой до возобновления работы — ровно то, что и требуется, потому что именно тогда старое число вводит в заблуждение.

**Признак пересмотра.** Правило «прошедший `resetsAt` = закрывшееся окно» опирается на то, что Claude Code обновляет `resets_at` вовремя. Замер: на 218 записях истории ни одна не несла уже прошедшего сброса в момент записи, ближайший подход — 3,6 минуты до него. Но история хранит только недельное окно, а пятичасовое катится в 33 раза чаще и в неё не попадает.

> Если встретится снимок, у которого `resetsAt` в прошлом, а процент явно относится к новому окну, — правило неверно для пятичасового окна.

Тогда нужна либо отсрочка, либо доверие проценту вместо момента. До тех пор — не усложнять. Сторож `aWindowAboutToCloseKeepsItsNumber` держит границу с другой стороны: окно, закрывающееся через секунду, число сохраняет.

**Все три величины показываются как израсходованное.** Это правило, а не деталь вёрстки: в одном столбце не должно стоять двух противоположных вещей. Раньше лимиты показывали остаток, а контекст — заполнение, и в соседних строках «больше» означало то «лучше», то «хуже». Читать такое можно только с оговоркой, а оговорку виджет сообщить не успевает.

Заодно это выравнивает нас с официальной панелью Usage в приложении Claude, которая тоже показывает израсходованное, — см. 8.1.

**Лимиты — от расхода:**

| Израсходовано | Уровень | Цвет |
|---|---|---|
| < 50% | healthy | зелёный |
| 50–80% | warning | жёлтый |
| 81–99% | critical | красный |
| 100% | depleted | серый |

**Контекст — от расхода, пороги строже:**

| Израсходовано | Уровень | Цвет |
|---|---|---|
| < 50% | healthy | зелёный |
| 50–70% | warning | жёлтый |
| > 70% | critical | красный |

Полярность теперь общая, разными остались только допуски. Контекст переходит в красное на 70%, лимит — на 81%: выше 70% модель начинает хуже удерживать детали из начала диалога, а лимит по-настоящему опасен лишь у самого исчерпания.

**Пороги лимитов — та же граница, что и в прежней редакции**, переписанная от расхода: «остаток > 50 / 20–50 / 1–20 / 0» даёт в точности «расход < 50 / 50–80 / 81–99 / 100». Смена полярности не должна была поменять цвета местами, и не поменяла.

**Полоска всегда равна показанному числу и заполняется по мере расхода.** Раньше у лимитов она опустошалась. Полоска, растущая в одной строке и убывающая в соседней, — тот же дефект, что и смешанные величины, только в графике.

**Подписи обязаны называть величину.** «Week used», «Context used», «used · resets Чт 07:00». Полярность должна читаться с виджета, а не выводиться из знания о том, как он устроен.

Конкретные значения цветов брать из системных `Color.green` / `.yellow` / `.red` — они сами адаптируются к светлой и тёмной теме и к настройкам доступности. Свою палитру заводить не нужно.

**Доступность:** цвет не должен быть единственным носителем смысла. Уровень дублируется формой индикатора либо подписью — иначе виджет бесполезен при дальтонизме.

### 8.1 Сверка с панелью Usage

Единственный доступный способ проверить, что виджет не врёт, — сличить его цифры с панелью Usage в приложении Claude. Другого независимого источника у нас нет: `rate_limits` недокументирован (раздел 14), и ошибка в нашей арифметике внешне неотличима от правильного ответа.

**Поэтому сверка обязана быть проверкой в одно действие.** Панель Usage показывает израсходованное; виджет теперь тоже. Числа должны совпадать **напрямую, без вычитания из ста**. Расхождение сразу означает ошибку — в разборе, в округлении или в выборе окна, — а не «так и должно быть, у нас же остаток».

Прежняя редакция требовала считать в уме: панель говорит 64%, виджет показывал 36%, и совпадение подтверждалось сложением. Такая сверка не делается мимоходом, а значит не делается вовсе.

**Подписи в панели и в виджете не совпадают дословно**, поэтому соответствие фиксируется здесь целиком. Без этой таблицы человек, сверяющий цифры впервые, потратит минуту на догадки — ровно то, чего раздел и должен избежать.

| Строка виджета | Панель Usage | Сверяется |
|---|---|---|
| `5-hour used` | **Current session** | да, число в число |
| `Week used` | **All models** | да, число в число |
| `Context used` | — | нет: это заполнение окна контекста, а не лимит подписки |
| — | **Fable** | нет: в JSON статуслайна нет разбивки по моделям (раздел 2.1) |

Два разночтения в названиях стоят того, чтобы их проговорить.

**«Current session» — это пятичасовое окно аккаунта, а не сессия диалога.** Терминология Anthropic, и именно из-за неё строка виджета называется `5-hour`, а не `Session`: рядом в подвале стоит `this session` про стоимость, и там слово означает уже сессию Claude Code. Одно слово в двух значениях — источник ошибок при сверке.

**«All models» — это недельное окно**, общее по всем моделям. Отдельная строка **Fable** в панели показывает недельный лимит по конкретной модели; в статуслайне такого поля нет и не будет (раздел 2.1), поэтому в виджете её нет. Отсутствие строки — не дефект, и сверять её не с чем.

Контекст и стоимость в панели Usage не показываются вовсе. Это отдельная причина не смешивать их с лимитами в одном столбце разной полярности: у половины строк есть внешний эталон, у половины нет, и различать их надо с одного взгляда.

Расхождение в один процент допустимо: экспортёр округляет дробные значения (раздел 2.1), панель может округлять иначе. Расхождение больше единицы — дефект.

### systemSmall (164×164)

Только недельный лимит. На таком размере читается ровно одно число.

- Заголовок: иконка уровня + «Week used»
- Крупно: **израсходовано** в процентах, 34pt, вес medium
- Полоска прогресса, заполняется по мере расхода
- Подпись: «used · resets ср 3:00»

Цифра растёт к концу недели, а не убывает. Подпись обязана читаться в ту же сторону: «used», а не «осталось».

или остаток; проверено при аудите источников. Довод свой: две противоположные
величины в одном столбце заставляют читателя каждый раз вспоминать, в какую
сторону смотреть, а виджет существует ради взгляда без раздумий.

### systemMedium (344×164)

- Шапка: модель и уровень усилий
- Три строки-полоски: `5-hour used`, `Week used`, `Context used`. У каждой подпись, полоска, процент, вспомогательное значение
- Подвал через разделитель: `this session:` со стоимостью и долей кеша слева, возраст данных справа

**Имени проекта в шапке нет намеренно.** Экспортёр глобальный, все сессии пишут в один снимок, и проект относится к последней отрисовавшейся сессии, а не к виджету целиком — в заголовке он читался как «этот виджет про проект X». Теперь он стоит вспомогательным значением у строки контекста, к которой действительно относится.

**Пятичасовое окно называется `5-hour`, а не `Session`.** Слово «сессия» занято сессией Claude Code, которой принадлежат контекст и стоимость; пятичасовое окно принадлежит аккаунту целиком. Одно слово в двух значениях по соседству — источник ровно той путаницы, которую снимает подпись `this session` в подвале.

### systemLarge (344×344)

Всё из среднего плюс блок прогноза:

- График накопленного расхода недели, линия прогноза пунктиром
- Подпись с датой исчерпания либо «хватит до сброса»
- Подвал расширенный: стоимость, токены, доля кеша

### Нажатие открывает окно, и глубокой ссылки нет

**ОТСТУПЛЕНИЕ ОТ РЕКОМЕНДАЦИИ, ПРИЧИНА ЗАПИСАНА.** Human Interface Guidelines
просят, чтобы нажатие на виджет открывало приложение «в нужном месте», и
WidgetKit даёт для этого `widgetURL(_:)`. Мы его не ставим: у приложения одно
окно и в нём нет разделов, вести некуда. Появятся разделы — появится и
`widgetURL`, причём у среднего и большого размеров он должен вести к тому
ряду, по которому нажали.

### Требования к вёрстке

- **Никаких фиксированных ширин под текст.** Немецкий длиннее английского примерно на треть, японский короче. Использовать `layoutPriority`, `minimumScaleFactor(0.8)` и `lineLimit(1)`.

  **`minimumScaleFactor` — разрешение сжаться, а не указание, кому сжиматься.** Если в ряду два текста и никому не задан приоритет, вёрстка сама выбирает, кому дать меньше запрошенного, и выбор может оказаться не тем. В шапке окна так и вышло: бейджу дали право сжиматься, замер сходился, а обрезало заголовок — «Usage Widget for Claude C…» рядом с самым широким из четырёх бейджей, увидено в окне при часовом возрасте. Кто уступает, задаётся `layoutPriority`; допуск на сжатие имеет смысл только на том, кто уступает.

  Отсюда же и форма проверки: мерить надо сумму — влезает ли ряд целиком, — а не одно слагаемое против остатка. Сумма верна независимо от того, кого вёрстка выберет сжимать.
- **Вторичные строки набираются `caption2`, и это отступление.**

  **ОТСТУПЛЕНИЕ ОТ РЕКОМЕНДАЦИИ, ПРИЧИНА ЗАПИСАНА.** `widgetkit-creating-views.md`
  называет для виджетов четыре стиля — `headline`, `title`, `body`, `caption`, —
  и `caption2` в этот перечень не входит. Мы его используем: подписи под
  шкалами, подвал, вердикт оценки.

  Речь не о размере. По таблице «macOS built-in text styles» из
  `hig-typography.md` оба стиля на macOS равны **10 pt**, что и есть
  минимальный размер для платформы; различаются они начертанием: `Caption 1` —
  Regular, `Caption 2` — Medium. Переход на `caption` не увеличил бы текст, а
  облегчил бы его.

  Замерено и просмотрено: строки влезают в обоих начертаниях на всех шести
  языках — `caption` даже на 2–3 pt уже. Но вторичные строки рисуются серым
  (`.secondary`), и на плотной плитке Regular по серому читается хуже
  Medium — в тёмной теме заметно сильнее, где и фон, и текст уже
  низкоконтрастны. Сравнение рендеров среднего и большого размеров в обеих
  темах показало это однозначно.

  Итог: остаёмся на `caption2` ради читаемости и расходимся с перечнем стилей.
  Пересмотреть, если Apple изменит вес `Caption 2` или если вторичные строки
  перестанут быть серыми.

- **Цифры моноширинные:** `.monospacedDigit()` на всех числах. Иначе при смене 9% на 10% макет дёргается.
- **Строки шкал — одна таблица, а не три строки.** На средней плитке и в окне три ряда «значок · подпись · шкала · процент · отсчёт» собраны в `GaugeTable` (`Grid`): столбец подписей — по самой широкой подписи, шкалы начинаются и кончаются вместе, проценты и отсчёты выровнены по правому краю своих столбцов. Ширина столбца — по самой широкой ячейке (`apple/swiftui-grid.md`), числом не задаётся, так что правило про фиксированные ширины не нарушено. Раньше каждый ряд верстался сам по себе, и три подписи разной длины давали три шкалы, начинавшиеся в трёх местах, — увидено на столе 18 августа 2026. Держит `RowCompositionTests`: начала и концы шкал и правый край строк совпадают на всех шести языках.

  Два замера по дороге, оба записаны в коде: `layoutPriority(1)` у подписи в сетке нужен — без него сетка отдаёт ширину шкале и режет подпись; `layoutPriority(2)` у последнего столбца в сетке вреден — с ним гибкий столбец шкалы не забирает остаток и таблица кончается на 283 pt из 330.
- Все отступы кратны 2, внутренний отступ виджета 14–16pt.

  **ОТСТУПЛЕНИЕ ОТ РЕКОМЕНДАЦИИ, ПРИЧИНА ЗАПИСАНА.** Human Interface
  Guidelines называют стандартным полем 16 pt и говорят, что на рабочем столе
  Mac поля меньше, но величины для Mac не публикуют. Наши 14 pt выбраны
  замером на живой плитке, системные поля при этом отключены
  (`contentMarginsDisabled`), иначе они складываются с нашими. Опереться
  здесь не на что: числа для macOS у Apple нет, есть только направление
  «меньше, чем 16».
- Поддержка светлой и тёмной темы обязательна, проверять обе.

### 9.1 Покрытие видов: граница проведена и дальше не двигается

**Решение: за пределы трёх ярусов из `Docs/rendering-checks.md` не идём.** Это не отложенная работа и не признание нехватки времени — это граница, проведённая по классам дефектов, которые в проекте действительно случались.

Каждый из них закрыт, и закрыт самым дешёвым средством из возможных:

| Класс дефекта | Чем закрыт |
|---|---|
| Обрезанный текст в чужом языке | ярус 1 — метрики текста, шесть языков разом, ноль изображений |
| Формулировка и порядок того, что произносит VoiceOver | ярус 2 — текстовый эталон, читаемый в диффе |
| Геометрия графика оценки | ярус 3 — пять изображений, один размер, одна тема, один язык |

Всё, что остаётся в видах после этого, — **композиция**: где какой блок стоит, какие между ними отступы, как они переносятся. Покрывать композицию проверками значит заводить сетку эталонов на размеры × темы × языки × состояния, а она отвергнута в `Docs/rendering-checks.md` числами, а не вкусом:

- тридцать шесть файлов и 1,4 МБ на одних только языках, девяносто шесть и около 5 МБ с состояниями оценки;
- любая правка подписи перегенерирует языковой столбец целиком — такое случалось дважды в ещё не опубликованном проекте, и каждый раз это был бы дифф на тридцать шесть файлов, который никто не читает;
- порог допуска не работает: шесть секунд хода часов сдвигают 0,364 % пикселей, а обрезанное многоточием слово — того же порядка.

**Признак, по которому решение можно пересмотреть:** дефект композиции, дошедший до пользователя. Не «мог бы дойти», а дошедший. До тех пор ярусы 1–3 — это весь объём, и возвращаться к вопросу не нужно.

**Признак сработал 7 августа 2026.** Дважды за день, и оба раза не так, как ожидалось: не «эталон бы поймал», а «ни один эталон поймать не мог». Отсюда 9.2 — не четвёртый ярус, а другая ось.

### 9.2 Размерные требования проверяются только на живой системе

**Правило.** Всё, что просит у вида точный размер, обязано быть проверено на работающей системе. В тестовом процессе такая проверка невозможна не по недосмотру, а по устройству: WidgetKit заранее архивирует состояния вида (`_ArchivedViewHost.archiveStates`), и именно в этом шаге размерные требования разрешаются. В процессе проверок этого шага нет вовсе — там вид рисуется обычным способом и рисуется правильно.

К размерным требованиям относятся:

- `GeometryReader` — читает предложенный размер;
- `.fixedSize()` — требует идеальный размер;
- `.frame` с жёсткими значениями — назначает размер;
- всё прочее, что задаёт или спрашивает точную величину, а не долю.

**Два случая одного дня, оба в одном классе, оба невидимые для 227 проверок:**

| | утро | вечер |
|---|---|---|
| Что стояло | `GeometryReader` в шкале | `.fixedSize()` на строке с динамической датой |
| Исход | расширение падало на каждой отрисовке | средняя плитка чёрная |
| Что видел рабочий стол | последний удачный кадр — «данные устарели» | тёмный прямоугольник |
| Что видел лог | 27 отчётов о падении | ничего |
| Что видели проверки | зелено | зелено |

Второй опаснее первого. Падение оставляет отчёт с трассой; пустота не оставляет ничего — ни отчёта, ни строки в журнале, ни ошибки от демона: `chronod` пишет `reload: succeeded` и `Cache hit` для всех трёх семейств.

**Почему `.fixedSize()` ломает именно динамическую дату.** У неё нет идеального размера: что будет написано — «5 дн 10 ч» или «2 мин» — решает система в момент отрисовки, а не код в момент сборки вида. Требование «займи ровно столько, сколько тебе нужно» не имеет ответа, и архивация отдаёт пустую плитку целиком, а не пустую строку. *Механизм не подтверждён источником* — в документации `archiveStates` не описан; подтверждено поведение: пять сборок, различающихся одной строкой (раздел 5.1).

Проверено разделением: та же строка со статическим текстом и `.fixedSize()` рисуется; та же динамическая дата без `.fixedSize()` рисуется и продолжает считать. Ломает сочетание.

**Защита ширины остаётся, но с другой стороны.** Шкала держит `minWidth: 40` — пол под тем, что важно, вместо потолка над тем, что неважно. Ради этого `.fixedSize()` и ставился; замена сохраняет цель и снимает требование.

### 9.3 Чем смотрят на живую плитку

Инструмент найден 7 августа и до того дня отсутствовал: за весь проект ни одна проверка ни разу не видела нарисованную плитку.

**Плитку на рабочем столе снять нельзя.** Своего окна у неё нет — её собирает композитор; слой `Dock`, которому она принадлежит, снимается пустым (проверено: 126 966 непрозрачных пикселей, и все они — панель Dock внизу экрана).

**Плитку в Центре уведомлений — можно.** Виджет, добавленный в Центр уведомлений, владеет настоящим окном, и оно снимается по идентификатору:

- окно принадлежит процессу с бандлом `com.apple.notificationcenterui` — это и отличает плитку от окна самого приложения, у которого похожее имя и похожее содержимое;
- имя окна — отображаемое имя виджета, каким оно было в момент добавления: у нас там до сих пор «Gauge for Claude Code», хотя виджет переименован. Тот же кэш метаданных, что держит старую иконку в галерее;
- размер окна — 360×180 для среднего, 180×180 для малого; это размеры Центра уведомлений, они не совпадают с размерами плиток рабочего стола из таблицы выше.

`Scripts/tile-probe.swift` делает это целиком: находит окно, снимает **только его** (не экран — за окном чужая работа), считает долю пикселей ярче 0,5 и отвечает одним из трёх:

| Исход | Код | Когда |
|---|---|---|
| нарисовала | 0 | доля ярких ≥ 1 % |
| пусто | 1 | доля ярких < 1 % |
| судить не по чему | 2 | окна нет — виджет не добавлен в Центр уведомлений |

Третий исход обязателен и не должен молчать: проверка, которая при ненайденном окне отвечает «всё хорошо», — это ровно тот дефект, который искали весь день, только в самой проверке.

**Откуда порог.** Замерено на четырёх сборках одной и той же плитки: сломанная — 0,023 % ярких пикселей (13 из 55 816, сглаживание на скруглении угла), три исправных — 4,90 %, 5,12 % и 5,00 %. На плитке около восьми строк текста, значит одна строка — примерно 0,6 %; порог в 1 % означает «меньше двух строк текста», то есть не плитка. Он в двадцать раз выше пустой отметки и впятеро ниже рабочей, и это не середина между двумя числами, а высказывание о том, что должно быть на экране.

Проверка проверена подделкой, а не рассуждением: на снимке сломанной сборки — код 1, на снимке исправной — код 0, и на живой системе перед починкой она падала, а после — проходит. Встроена в `Scripts/reinstall.sh`: установка не называет себя удачной, пока плитка не нарисовала содержимое.

## 10. Локализация

Механизм: String Catalogs (`.xcstrings`), по одному на таргет.

**Основной язык — английский.** Русский равноправный перевод, не источник.

Стартовый набор: `en`, `ru`, `ja`, `zh-Hans`, `es`, `de`.

Даты, время, проценты и разделители разрядов форматировать **только** через `Date.FormatStyle`, `Measurement` и `NumberFormatter` с системной локалью. Никакой ручной склейки строк вида `"\(hours)ч \(minutes)м"` — в японском и немецком это выглядит неправильно.

Относительное время («2 минуты назад») — через `RelativeDateTimeFormatter`, он локализован из коробки.

**Числа следуют региону, а не языку интерфейса.** Форматтеры берут `Locale.autoupdatingCurrent`, поэтому при английском интерфейсе и русском регионе стоимость останется «48,85 US$». Это поведение Apple по умолчанию и оно правильное: язык выбирают для чтения, разделитель разрядов — для привычки.

**Данные — не строки интерфейса.** Отформатированное число, имя проекта, путь к файлу выводятся через `Text(verbatim:)`. Иначе SwiftUI попытается найти «64 %» в каталоге как ключ перевода: работать будет, но каталог засорится значениями, которых там быть не должно.

Отдельного внимания требует плюрализация в русском: 1 минута, 2 минуты, 5 минут. В String Catalogs для этого есть варианты по правилу множественного числа — заполнить их, а не игнорировать.

## 11. Первый запуск

Самое слабое место продукта: виджет не заработает, пока пользователь не пропишет строку в конфиге Claude Code. Экран первого запуска должен вести за руку.

Три шага:

1. **Проверка.** Приложение ищет `~/.claude/settings.json`. Найден — показывает, что Claude Code обнаружен. Не найден — объясняет, что нужен Claude Code, со ссылкой.
**Установщик пишет по цели символической ссылки.** Если `~/.claude/settings.json` — ссылка в репозиторий dotfiles (stow, chezmoi, yadm — обычное дело у терминальной аудитории), атомарная запись подменила бы саму ссылку обычным файлом: связь молча рвётся, настоящий конфиг остаётся без `statusLine`, и причина неочевидна. Поэтому ссылка разыменовывается перед записью, а резервная копия делается копированием содержимого, а не файла: копия-ссылка указывала бы на файл, который мы вот-вот перезапишем.

Если сохранить ссылку нельзя — цель недоступна на запись, — экран говорит об этом **до** нажатия кнопки, а не после.

2. **Установка.** Кнопка «Настроить автоматически»: приложение делает резервную копию `settings.json`, подставляет путь контейнера вместо `__GROUP_DIR__` в шаблоне экспортёра, кладёт результат в `~/.claude/ccwidget-export.py`, выставляет права на исполнение и дописывает ключ `statusLine`. Рядом кнопка «Показать инструкцию вручную» с командой в буфер обмена — для тех, кто не хочет пускать приложение в свои конфиги. Путь контейнера показывается на экране, чтобы подстановку можно было сделать руками.
3. **Ожидание.** Экран с крутящимся индикатором и текстом «Запустите Claude Code и отправьте любое сообщение». Приложение следит за появлением `snapshot.json` и при успехе показывает первые живые цифры и напоминание добавить виджет, если его ещё нет на столе. Кнопки «Добавить виджет» нет: программно поставить виджет на рабочий стол macOS не позволяет.

Существующий ключ `statusLine` нельзя молча затирать — если там что-то есть, спросить и предложить резервную копию.

**Если хирургическая правка не удалась, сказать об этом — на установке и на удалении одинаково.** Файл один и тот же, риск один и тот же: при перестроении теряются порядок ключей и отступы, а у терминальной аудитории конфиг нередко лежит в dotfiles под контролем версий. Установка сообщала об этом с самого начала, удаление молчало; асимметрия была недосмотром, а не решением. `RemovalReport.editWasSurgical` несёт тот же признак, что и `Report.editWasSurgical`, и окно печатает ту же фразу.

**«Наш» ключ — это точное совпадение команды, а не упоминание пути.** Удаление — единственная операция, где ошибка опознания что-то разрушает, и именно она долго опознавала по подстроке: `Scripts/uninstall.sh` искал `ccwidget-export.py` во всём `settings.json` и считал своим любой `statusLine`, если экспортёр упоминался хоть где-нибудь — в чужой обёртке, которая вызывает его и дописывает своё, или в хуке. Приложение всё это время сравнивало `statusLine.command` целиком (`Installer.statusLineState`), то есть запасной путь был слабее основного. Теперь оба сравнивают одинаково — с точностью до написания пути: `~/.claude/…`, `$HOME/.claude/…` и абсолютный путь называют один файл, а документация статуслайна свой собственный пример пишет как раз с тильдой (`claude-code/statusline.md`). Состояний шесть: нет файла, не разбирается, ключа нет, наш, чужой и «форма, которую мы не умеем читать». Своим считается ровно одно из шести.

**Файл экспортёра удаляется, только если на него больше никто не ссылается.** Правило одно на все случаи: после мысленного удаления нашего ключа `settings.json` не должен упоминать путь экспортёра нигде. Иначе чужая обёртка или хук остаются звать файл, которого нет, — молчаливая поломка вместо честного «оставили, вот почему». Нечитаемый `settings.json` останавливает удаление целиком: раз о ключе ничего сказать нельзя, экспортёр тоже не трогаем.

**Решение принимается в момент действия, а не до подтверждения.** Между планом и ответом на «Continue?» файл может измениться, поэтому классификация повторяется перед самой правкой и отказывается удалять то, что перестало быть нашим. Проверка `Scripts/check-uninstall.sh` производит все состояния, включая эту гонку, на подставном `HOME`.

### 11.0 Экран настройки знает, что человек здесь не впервые

Если в каталоге обмена лежит снимок или история, а экспортёра нет, значит настройку **сняли**, а не не делали никогда: оба файла пишет только экспортёр, и обычное удаление их не трогает — их убирает либо кнопка «Удалить и стереть историю», либо `brew uninstall --zap`. Экран говорит об этом одной фразой и продолжает предлагать настройку.

**Зачем.** Обновление через Homebrew снимает настройку по пути — станса `uninstall` у каска сортируется раньше приложения, которое она заменяет (`cask/artifact/abstract_artifact.rb`, комментарий в `sort_order`; при обновлении пропускается только директива `signal`). Человек с тремя неделями истории получал экран для новичка и ни одного намёка на то, что произошло.

**Причина во фразе не названа, и это не осторожность ради осторожности.** То же состояние остаётся после кнопки «Удалить…», поэтому «вас обновили» было бы догадкой в виде объяснения. Названо наблюдаемое — данные есть, настройки нет, — и общий механизм, который это чаще всего объясняет.

Проверок шесть на значение и одна на отрисовку. Последняя нужна отдельно: значение может быть правильным, а фраза не попасть на экран, и шесть проверок значения этого не заметили бы.

### 11.1 Строка состояния делится, а не отбирается

**Установка виджета не должна стоить человеку его строки.** Экспортёр не печатает ничего своего — он пишет файл и выходит, — поэтому захват ключа `statusLine` оставлял строку пустой. Для аудитории, у которой там `ccstatusline` или свой скрипт, это отъём под видом функции.

**Как устроено.** При установке прежняя команда читается из `statusLine.command` и подставляется в экспортёр как литерал Python — тем же способом, что и путь контейнера, и по той же причине: строка содержит кавычки чаще, чем не содержит, а файл исполняется на каждой перерисовке. Экспортёр вызывает её через оболочку, отдаёт ей тот же stdin, что получил сам, и печатает её stdout без изменений. Через оболочку — потому что так её запускает сам Claude Code: документация статуслайна говорит, что поле `command` «runs in a shell», и её же примеры — конвейеры с `jq`.

**Порядок намеренный: сначала своё, потом чужое.** Запись снимка занимает около двадцати миллисекунд и не может заблокироваться; чужая команда может висеть до таймаута. Если бы она шла первой, сломанный статуслайн останавливал бы и получение данных виджетом — один дефект превращался бы в два. Так виджет продолжает работать, пока чужая строка сломана, а приглашение опаздывает на двадцать миллисекунд, которых никто не видит.

**Таймаут три секунды.** Статуслайн перерисовывается десятки раз в минуту, поэтому висящая команда висла бы на каждой; трёх секунд хватает скрипту, который дёргает git, и мало для того, чтобы сломанный превратил работу в заморозку.

**Отказ чужой команды записывается, а не проглатывается.** Файл `chain-failed.json` в контейнере: когда началось и что случилось — код возврата, таймаут или невозможность запустить. Печатает `ccwidget-dump`. Экспортёр не может сказать это на stdout: всё, что он печатает, попадает в приглашение. Симптом при этом — пустая строка в терминале, и винить в нём будут виджет, поэтому молчать здесь нельзя вдвойне.

**Где команда хранится и почему именно там.** В самом экспортёре, и читается обратно оттуда же. Это то, что делает переустановку безопасной: `reinstall.sh` вызывает установку десятки раз в день, и к этому моменту статуслайн уже наш — значит вопрос «что подцеплять» ответил бы «самих себя», а запись такого ответа либо потеряла бы чужую команду, либо заставила бы экспортёр вызывать себя вечно.

**Установка меняет только `command`.** Раньше она писала новый объект целиком и выбрасывала `padding`, `refreshInterval` и остальное — чужие настройки, до которых нам нет дела. А удаление не могло вернуть то, чего установка не сохранила.

**Удаление возвращает прежнюю команду на место.** Не удаляет ключ, а ставит в него то, что было до нас, оставляя остальной объект как есть. Оба пути — кнопка в приложении и `Scripts/uninstall.sh` — делают это одинаково и читают команду из одного места.

**Расхождения, оставленные сознательно.** Их два, оба в сторону «скрипт строже». Приложение удаляет экспортёр всегда, а скрипт — только когда на него никто не ссылается: чтобы свести, нужна новая строка в окне удаления, а окно правится отдельно. И `Installer.statusLineState` сравнивает только абсолютный путь, то есть ключ, записанный с тильдой, приложение считает чужим и при удалении оставит. Правка очевидная, но она делает приложение удаляющим больше, а не меньше, и трогает ветку экрана установки — отдельное решение владельца, а не побочный эффект починки скрипта.

## 12. Порядок работ

Этапы упорядочены так, чтобы после каждого было что-то работающее и проверяемое.

**Этап 1 — данные.** Скрипт-экспортёр, каталог обмена, модели `Snapshot`, чтение из `SnapshotStore`. Проверка: консольная утилита печатает разобранный снимок.

**Этап 2 — виджет-минимум.** Таргет расширения, песочница расширения, `TimelineProvider`, только `systemMedium`. Проверка: виджет на рабочем столе показывает живые цифры и обновляется.

**Этап 3 — остальные размеры.** `systemSmall` и `systemLarge` без прогноза, полировка вёрстки, тёмная тема.

**Этап 4 — прогноз.** `HistoryStore`, усечение, регрессия, график в большом размере.

**Этап 5 — демон и свежесть.** `SnapshotWatcher`, принудительная перезагрузка, деградация при устаревании данных.

**Этап 6 — первый запуск и локализация.** Онбординг, шесть языков, проверка вёрстки на немецком и японском.

**Этап 7 — выпуск.** README со скриншотами, сборка релиза, формула для Homebrew, публикация.

Этапы 1 и 2 — это и есть «виджет за вечер». Остальное наращивается.

## 13. Чего в первой версии не будет

Зафиксировано сознательно, чтобы не расползлось:

- **Снимок на сессию и настраиваемый виджет.** Экспортёр глобальный: все сессии Claude Code пишут в один `snapshot.json`, побеждает последняя отрисовавшаяся. Лимиты и прогноз от этого не страдают — они общие для аккаунта. Контекст, стоимость, доля кеша и имя проекта посессионные и мигают между сессиями; в первой версии это принято и честно подписано (проект у строки контекста, `this session` в подвале).

  Полное решение — хранить снимок на сессию — само по себе мигание не лечит: «последняя активная» ведёт себя так же. Смысл оно приобретает только вместе с настраиваемым виджетом на `AppIntentConfiguration`, приколоченным к выбранному проекту. **Обе фичи идут вместе во второй версии, порознь не имеют смысла.**

  Показ всех активных сессий в большом размере — не раньше посессионного хранения и **не ценой прогноза**: место в большом размере занято прогнозом, а он и есть главное отличие продукта.

- ~~**Фоновый режим.**~~ **Сделано 17 августа 2026 в 0.3.3, раньше плана, по решению владельца — отступление, названное отступлением.** Здесь стояло «версия 1.1» с доводом: автозапуск требует доверия, которого у нового инструмента ещё нет. Довод не отменён, он выполнен иначе — переключатель **выключен по умолчанию**, так что доверие спрашивают у того, кто уже пользуется, а не берут у того, кто только поставил.

  Что при этом изменилось против плана: `LSUIElement` не понадобился — приложение остаётся обычным, а окно не показывается при запуске по входу, определяя запуск по `NSApplication.launchIsDefaultUserInfoKey`. Цена отката: убрать переключатель, `LoginItem`, ветку в `AppDelegate` и снятие регистрации при удалении; данные пользователя при этом не затрагиваются, кроме одной записи элемента входа, которую снимает то же удаление.

- ~~**Композиция со сторонним статуслайном.**~~ **Сделано 17 августа 2026, раньше плана — см. 11.1.** Здесь стояло «версия 2», и это было ошибкой приоритета: цена уже платилась. Уборщик пришлось учить не удалять чужую обёртку, которая вызывает экспортёр, — то есть люди, делающие так, в модели уже были, — а первое, что заметит новый пользователь, это исчезнувшая строка в терминале. Работа заняла партию, а не версию.

- Мультипровайдер. Codex, Gemini и Copilot дают расход в токенах, но не квоты плана — это другой тип данных и другой интерфейс. Версия 2.
- Недельный лимит по конкретной модели. В статуслайне его нет.
- Разбивка контекста по категориям. Требует разбора файла транскрипта, отдельная большая работа.
- Уведомления. Их закрывает ClaudeBar, дублировать в первой версии незачем.
- Сборка под Mac App Store. Возвращаемся к ней, если проект наберёт пользователей.
- Автообновление через Sparkle. Достаточно Homebrew.

## 14. Открытые вопросы

**Только терминальный Claude Code.** `statusLine` вызывается лишь в терминальной версии — **наблюдение**, прямого утверждения об этом в документации статуслайна нет. У пользователя десктопного приложения экспортёр не запустится никогда, и виджет останется пустым навсегда — не «данные устарели», а вообще без единой цифры. Это отсекает часть аудитории, и умолчать об этом нельзя: **в README ограничение должно стоять в первом абзаце, до инструкции по установке.** Снимается решением вопроса о фоновом опросе лимитов — но только тем решением, которое укладывается в договорные рамки, описанные ниже. Приоритет высокий, пространство решений узкое.

**Свежесть при закрытом Claude Code.** Единственная нерешённая проблема архитектуры. Требует исследования: можно ли получить лимиты без интерактивной сессии. Кандидаты — разбор кеша в `~/.claude`, headless-режим CLI, наблюдение за файлами транскриптов. До решения виджет честно показывает возраст данных.

**У этого вопроса есть не только техническое ограничение, но и договорное, и оно жёстче.** Consumer Terms запрещают доступ к сервису автоматическими или нечеловеческими средствами — ботом, скриптом или иначе, — кроме доступа по ключу Anthropic API или с явного разрешения Anthropic. В январе 2026 по этому запрету заблокированы OpenClaw, OpenCode, Roo Code и Goose за извлечение OAuth-токенов из подписки.

**Номера пункта здесь нет намеренно.** Раньше тут стояло «пункт 3.7», и такой нумерации в договоре больше не существует: в редакции от 8 октября 2025 запрет живёт в разделе 3 «Use of our Services» ненумерованным пунктом списка. Прочитано 6 августа 2026 (`SOURCES.md`, живые источники). Ссылаться следует на формулировку и дату редакции — номер пункта в этом документе не пережил и года.

Нынешняя схема под запрет не попадает: виджет не обращается к моделям, не держит учётных данных и читает файл, который Claude Code сам подаёт команде `statusLine` — штатной точке расширения. Но добыча лимитов при закрытом Claude Code лежит вплотную к этой границе, и часть кандидатов её пересекает.

Рамки для будущей реализации:

- **Исключено безоговорочно:** извлечение токенов подписки, эмуляция клиента, любое обращение к внутренним эндпоинтам с учётными данными подписки. Это ровно то, за что блокировали перечисленные проекты.
- **Программный запуск CLI ради лимитов** — тоже автоматизированный доступ, даже если технически работает. Считать его допустимым по аналогии нельзя.
- **Допустимо только то, что опирается на официальные точки расширения**, как нынешний `statusLine`: механизмы, которые Claude Code сам предоставляет пользователю для настройки.
- **Перед реализацией — сверка с актуальной редакцией Consumer Terms**, а не рассуждение по аналогии с этим абзацем. Формулировки менялись дважды за год.

Это снимает часть повышенного приоритета, который вопрос получил вместе с ограничением аудитории: пространство допустимых решений оказалось заметно уже, чем выглядело.

**Правила использования товарных знаков Anthropic не сверены.** Software Directory Terms обязывают соблюдать отдельный документ Trademark Guidelines, но по прямым ссылкам он недоступен: `anthropic.com/trademark` и `anthropic.com/legal/trademark` отдают 404, в разделе Privacy and Legal статьи о знаках нет. Общий запрет на подразумеваемое партнёрство, спонсорство и одобрение закрыт оговоркой в README; конкретные правила именования остаются непроверенными. Ссылку стоит открыть со страницы Software Directory Terms, если приложение будет подаваться в каталог.

**Стабильность схемы статуслайна.** Формат недокументирован в части `rate_limits` и может измениться в любом выпуске Claude Code. Смягчение: `schemaVersion`, мягкий разбор, понятное сообщение вместо падения.

**Вторая настоящая история недели. После публикации.** Всё, что известно о поведении оценки на живых данных, известно из одной истории одного человека за 118 часов, и эта неделя ни разу не подошла к исчерпанию. Из неё измеримы ложные срабатывания и не измеримо главное — за сколько часов приходит предупреждение. Восемь синтетических профилей эту дыру не закрывают: профиль — гипотеза о том, как человек работает, и все восемь придуманы одним и тем же человеком.

Замер на этих восьми показал и конкретное место, где одной истории мало: пороги R² почти не задевают неделю, которая действительно исчерпывается (сигнал крупный против квантования в один процент), и задевают лёгкую неделю, которой ничего не грозит. То есть ворота срабатывают в основном не на тех, ради кого сделана оценка. Утверждать это на одной истории нельзя, а проверяется оно чужими данными сразу.

Что просить: `history.jsonl` — в нём нет ничего, кроме меток времени, процентов недельного окна и времени сброса. Ни путей, ни имён проектов, ни содержимого работы. Присланный файл прогоняется `./.build/ccwidget-replay` и даёт ту же таблицу, что и раздел 6 в `Docs/estimate-review.md`. Просьба уместна в README после выпуска, не раньше: до выпуска просить не у кого.

**Несколько машин на одном аккаунте — вопрос без ответа.** Лимиты принадлежат аккаунту, а снимок и история — машине: на каждой стоит свой экспортёр, пишущий в свой контейнер. Проценты придут верные на обеих (их присылает Claude Code), а вот история для оценки на каждой машине своя и покрывает только её работу. Значит прогноз строится по половине расхода, если человек работает с двух Mac, и об этом никто не предупреждён — ни `README`, ни окно.

Замечено сторонним читателем 7 августа 2026 как «первый практический вопрос, который у меня возник». Не проверено: второй машины у нас нет. Прежде чем чинить, надо понять, что тут вообще правильно — складывать истории (тогда нужен обмен между машинами, чего в проекте нет), показывать оценку только по своей машине с оговоркой, или не показывать вовсе при признаках второй машины. Первое противоречит «ничего не покидает вашу машину»; третье требует признака, которого в данных нет.

**Риск дублирования со стороны Anthropic.** В трекере Claude Code уже открыт запрос на индикатор контекста в десктопном приложении. Если его реализуют, часть ценности проекта исчезнет. Это аргумент за быстрый выпуск и за то, чтобы делать ставку на прогноз — его вряд ли добавят.

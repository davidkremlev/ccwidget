## What holds up

Stated specifically, because "the quality is high" is not a finding.

**The rules produce the checks, and the checks are of kinds most projects do
not have.** Not "there are tests" but: every enum case must be produced by a
check, every case must make an observable difference, documented behaviour must
fail when broken. `ObservableDifferenceTests` and `OutcomeCoverageTests` exist
because those rules exist, and neither has an equivalent in ordinary practice.

**`SOURCES.md` and the split between how-it-works and how-it-should-be-done.**
Thirty-four sources, a script that says what has gone stale, and an explicit
mark for what is unverified. A project where a claim about the platform must
carry a citation is rare.

**Instruments that look at the live system.** `tile-probe.swift` and
`check-widget-health.sh` measure what a test process cannot see at all. The
usual substitute is the sentence "checked by hand", carried for years.

**The estimate.** Three outcomes instead of two, hysteresis on the R² gate,
`ccwidget-replay`, and `Docs/estimate-review.md` with measured numbers behind
every threshold. It is the one part a neighbouring project could not reproduce
in an evening, and it is built more honestly than it had to be.

**The README.** The limitation — terminal Claude Code only — stands before the
installation instructions. It says plainly that four localizations have never
been read by a native speaker, that the views have no coverage, and that macOS
14 and 15 have never run the widget.

**No network code, with a sentinel in CI.** The claim that nothing leaves the
machine is checkable rather than asserted.

## The gap

**The engineering is ready to ship and there is no shipping.** Two facts follow
directly.

### 1. The repository has no off-machine copy

`git remote -v` is empty and `.git/refs/remotes` does not exist. Nineteen days
of work, 88 commits, some 11,400 lines of code and checks and 6,700 of prose,
on one disk. The README already links to a GitHub repository, and that link was
dead in a way nobody had noticed: it named `illVminat`, which is the *display
name* on the profile, while the handle is `davidkremlev`. The account behind the
link returned 404, not the path.

Nothing else is holding a copy either, and this was checked rather than
assumed. `tmutil destinationinfo` reports no Time Machine destination. iCloud's
Desktop & Documents sync is on, but the project is not in the folder it syncs:
`~/Documents` and `~/Library/Mobile Documents/com~apple~CloudDocs/Documents`
are two different directories here — different inodes, different contents — and
the project is in the local one. The cloud side holds an older "Документы —
MacBook Pro" folder instead.

`CLAUDE.md` records why a batch ends in a commit: on 7 August a `git checkout
Widget/` took away two batches of work. A commit defends against that. It
defends against a failed disk, a stolen laptop or a mistyped `rm -rf` not at
all.

**Severity: the most expensive open risk, and the cheapest to close.**

### 2. Today's audience is people who own Xcode

No signed build, no notarization, no Homebrew, no release behind a tag — the
two that exist, `v0.1.0-dev` and `v0.2.0-dev`, are development marks. The only
route in is `brew install xcodegen`, clone, build. That excludes most of the
people the widget is for. The README says so and `SPEC` 14 calls it the main
obstacle; while it stands, none of the quality above reaches anybody.

*Unverified:* that notarization requires Apple Developer Program membership and
a Developer ID. No source in `SOURCES.md` covers it; check before planning the
work. Builds are currently **arm64 only** — a release needs a universal binary
or Intel Macs on 14 and 15 fall away silently.

## Findings, worst first

### 3. The exporter takes the status line and prints nothing

Installing the widget costs the user their status line. For an audience running
`ccstatusline` or a script of their own that is a bad trade, and `SPEC` 13 puts
composition in version 2.

The priority looks wrong. The right implementation — remember the previous
command at install time, hand it the same stdin, print its output — is on the
order of fifty lines in the exporter plus one field in the config. Exit codes
and a timeout need care; that is a day, not a version. The cost is already
being paid: `uninstall.sh` had to be taught not to delete a wrapper that chains
the exporter, which means users who do this are already in the model.

### 4. Freshness with the window closed

The widget refreshes itself roughly every half hour; anything faster needs the
app's window open. For a widget about a quota that is the core of the value.
`LSUIElement` plus `SMAppService` — version 1.1 in `SPEC` — closes it with no
contentious step.

Separately, the research question of where limits come from with Claude Code
closed. Neighbouring tools read the local transcript files under `~/.claude`,
and reading files the user already has does not touch the service at all, so
the contractual frame in `SPEC` 14 does not apply to it. **To be measured, not
believed:** transcripts carry tokens, not the account's quota percentages, so
at best this is an approximation, and whether the approximation is good enough
is a measurement.

### 5. Two machines on one account

History is per machine, so the estimate is built from half the consumption and
nobody is warned. `SPEC` 14 records it as unanswered. The minimal honest step is
not a fix but an admission: a line in the window and in the README. A sign of a
second machine could be derived — the weekly percentage rising faster than the
local history explains — but that is a hypothesis and wants a measurement.

### 6. Three tile views and two app screens are in no test target

Not low coverage: a structural fact. `CCWidgetTests` in `project.yml` does not
list `SmallView.swift`, `MediumView.swift`, `LargeView.swift`,
`StatusView.swift` or `OnboardingView.swift`. **1617 lines that no check has
ever executed.**

The one defect that reached the desktop — the black medium tile of 7 August —
lived in exactly that seam. WidgetKit's archiving step cannot be reproduced in
a test process, but "MediumView is a header, three rows and a footer" is
checkable with the instruments already written for `GaugeRow` in
`RowCompositionTests`. Adding the files to the target and writing composition
checks is one batch, and it closes the largest blind sector in the project.

### 7. `CCWidgetEntry.failure` is written and read by nobody

Filled in three places in `Provider.swift`; no view, no check and no other line
reads it — verified by grep across the tree. When the snapshot cannot be read
the tile shows a generic "no data" and the reason is dropped. It does reach the
log, so this is not silence, but it is the second question of the end-of-batch
pass failing: a field nobody reads. And it is an unwritten branch rather than a
surplus field — the reason it carries is the one that once looked like "the
snapshot is missing" when the sandbox had doubled the path.

### 8. The version number lives in four places and nothing compares them

`project.yml` sets `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`;
`App/Info.plist` and `Widget/Info.plist` carry the literals `0.2` and `2`,
which override them. CI checks `minos` and does not check the version.

*Unverified:* that a mismatch between the app's version and the extension's
misbehaves — no source in `SOURCES.md`. The drift itself is certain either way.
Substituting `$(MARKETING_VERSION)` and adding one CI step ends it.

### 9. Five security findings remain, two of them the class fixed today

`Docs/security-audit-2026-08-07.md` items 2, 4, 5, 6 and 7 are open. Two are
the same shape as the uninstaller defect closed on 16 August — deleting what is
not ours:

- **#7** `pruneBackups` removes every `settings.json.bak-*` beyond the newest
  five, including one a person made by hand.
- **#4** "remove history" leaves `export-skipped.json`, which carries a
  fragment of `sessionId`.

**#5** is closed with text rather than code: a hash kept beside the file it
describes catches drift, not tampering, and the comment should say that.

### 10. No linter, and no release job

`swift-format` or `swiftlint` belongs in the `source` job. A separate workflow
should build universal, sign, notarize and attach a `.dmg` on a tag. Until it
exists every release is a manual procedure, and a manual procedure on a
one-maintainer project is performed differently every time.

### 11. One baseline records the machine's time zone; the rest is rounding

Found by the first CI run in the project's life, minutes after the push that
finding 1 asked for: four of the five chart baselines differed on the macOS 26
runner. Four measurements took that apart, and the answer is written up in full
in `Docs/rendering-checks.md` under *Step 0, answered* — the step that document
asked for and never got, because there was no remote to run it on.

In short: the runner is deterministic (two runs of one commit, byte-identical);
three of the four differences are **one unit of 255** on a handful of pixels;
and the fourth is a 76×16 block of caption text, which is the time zone.
`ChartBaselineTests` pins scale, colour scheme, locale and colour space and
does not pin a zone, so `chart-runs-out.png` carries Asia/Tashkent inside it.
Running the built bundle directly under `TZ=UTC` fails exactly one check of
227 — that one.

**The defect is the unpinned zone**, and it is the same shape as the locale,
which was made a parameter for this exact reason. Fixing it needs a `timeZone`
alongside the `locale` in `CCWidgetFormat.resetMoment` and one regenerated
baseline. With the zone out of the way the two machines draw the same picture
to within 40 pixels of 101,712 at delta 1 — noise a byte comparison cannot
tolerate and a pixel comparison can, by a factor of 179.

### 12. The minimum supported toolchain builds no icon, and says nothing

The macOS 14 job fails at *Check the bundle is complete*: no
`Contents/Resources/Assets.car`. The build itself reported no error and no
warning — `Fail on warnings` passed — so on Xcode 16.2 the icon is simply not
there.

Observed, not explained: whether Xcode 16 compiles the Icon Composer `.icon`
format at all is a claim about the toolchain and `SOURCES.md` has nothing on
it. What is certain is the effect — an app built on the minimum supported
toolchain ships without an icon, silently, and the CI step written for exactly
this ("both can go missing without the build saying a word") caught it the
first time it was ever executed.

**One of the three ways out is now closed, measured rather than assumed.**
Apple's own release notes say "Xcode 26 requires a Mac running macOS Sequoia
15.6 or later" (`apple/xcode-26-release-notes.md`, added to `SOURCES.md` on 16
August 2026), and the macOS 14 runner carries nothing newer than Xcode 16.2 —
the image was asked, and it lists 15.0 through 16.2 and nothing else. So
"raise the minimum Xcode" is not a toolchain decision at all: it raises the
floor for *building* the project to macOS 15.6, while the deployment target
can stay at 14. Two ways out remain:

- **A second icon source** — an `.icns` or an asset catalog for pre-26
  toolchains. Two artifacts of one icon that nobody compares is the class of
  defect this project finds weekly; it would need a check of its own.
- **Say it plainly**: on a toolchain older than Xcode 26 the app builds without
  an icon, and the bundle check knows which runner it is on. Cheap and honest,
  provided it is written down rather than left to be discovered.

### 13. The checks had never compiled on the minimum supported toolchain

The README says CI "builds the app and runs the checks on macOS 14 and on
macOS 26, so the code compiles and its logic runs on both". The first time that
job ever ran, the test target failed to compile on the macOS 14 image:

    Tests/AnnouncementTests.swift:251: cannot convert value of type 'Int'
    to expected element type 'Double'

An array of tuples whose first element is `(0.0, …)` and whose later elements
are `3600 * 2`: Swift 6.2 infers `Double` for those literals, Swift 6.0 does
not. One line, and it meant the checks had never once run on the oldest
toolchain the project claims to support — the app built there, the checks
never did.

Worth separating from the defect: the sentence in the README was not a lie
anybody told. It described a workflow that existed, was correct in its
intention, and had never executed, because the repository had no remote to run
it on. **A claim about CI is a claim about something that runs. Until it runs
once, it is a plan.**

### 14. What a pre-publication scrub found, and what it cost

Asked for before making the repository public: what is in the built app, what
is in the whole history, and what the security review's eight findings actually
say. All three were answered on 17 August; the eight are closed and recorded in
`Docs/security-audit-2026-08-07.md`. The other two found four things.

**In the built app**, two leaks of the same fact by different routes. The
Release build carried LLVM profiling instrumentation — `ENABLE_CODE_COVERAGE`
defaults to YES — and each of its 424 `__profc_` symbols holds the absolute
path of the source file it counts. The debug symbol table added 57 more as
`OSO` and `SO` entries. Between them the shipped binary named the account and
every folder above the project. **Neither is visible to `strings`**, which is
the part worth remembering: they live in the symbol table, so the honest test
is a byte search, and "I grepped it and it looked clean" would have been the
wrong answer to a question that had two answers.

**In the history**, a project name and a session id. `SPEC` 2.4 quotes a real
observation of two sessions fighting over one snapshot, and named the other
project — which is also the handle of a second GitHub account, so publishing
would have linked the two. A committed fixture's `sessionId` was the first
eight characters of a real Claude Code session UUID, while the review's summary
said the fixtures were synthetic.

**The rewrite.** Both were replaced throughout the history with `git
filter-repo` on 17 August, before the repository had ever been public — the
only moment when that is cheap. 110 commits, all four tags, the working tree
byte-identical afterwards, 241 checks passing, and a fresh clone of the remote
confirms all three strings are gone. One commit disappeared in the process: the
one whose entire content was the scrub, which became empty once the replacement
applied to everything before it.

**What was deliberately left.** The bundle identifier `dev.illvminat.ccwidget`,
which `CLAUDE.md` fixes as the project's name. The Developer ID in the
signature, which cannot be anonymous. Two eight-character session-id fragments
in `SPEC` 2.4, which are what that observation is about and identify nothing
outside the machine. And the README screenshots, which the README itself calls
real data — they show a session cost of $141.35, and that is a disclosure to
confirm rather than a leak to fix.

### 15. Upgrading the app does not upgrade the exporter, and nothing says so

Found while checking the status-line sharing on the live machine: the app was
reinstalled, its bundled template has the new code, and
`~/.claude/ccwidget-export.py` is still the old file. Of course it is —
`reinstall.sh` installs the app, and the exporter is written by *setup*, which
is a button somebody pressed once weeks ago.

That was harmless while nobody had a release. It is not harmless now. A person
who installs 0.4.0 over 0.3.1 keeps the exporter from 0.3.1, gets none of what
the new one does, and **nothing anywhere tells them.** The integrity check does
not: it compares the file against the hash recorded when that file was written,
so an exporter that is stale but unmodified reports `.matches`, which is true
and beside the point.

`Installer.Integrity` has four cases — `matches`, `changed`, `missing`,
`unknown` — and the state "written by an older version of this app" is none of
them. It wants a fifth, which by this project's own rules means a fifth
observable difference in the window and a fifth sentence in six languages, so
it is a batch rather than a line.

**Closed the same day, and it was worse than written above.** "Press Set up
automatically again" was not merely an answer nobody could be expected to know
— it was not available. That button lives on the setup screen, which the app
shows only while it is *not* configured. There is a *Reinstall the exporter*
button in the window, and it lives inside the banner that appears when the
exporter has been **modified**; an exporter that is merely old raises no banner,
so the button could not be reached at all. The owner found this by looking for
the button and not finding it.

The exporter now carries the version that wrote it — one comment line, stamped
at install the way the container path is — and `Integrity` has a fifth case for
"written by an older version of this app". It raises the banner, the banner says
which of the two things happened, and the button is the same button. Checked by
installing as 0.3.1 and asking as 0.4.0, which is the only way to see an upgrade
without shipping two apps, plus a template with no stamp at all standing in for
the releases before this one.

**And then the fix shipped broken, which is the part worth keeping.** The owner
pressed the button and the banner stayed. The button had worked — the exporter
was rewritten, stamped and hashed — and the *verdict* was wrong: the stamp read
`# Written by ccwidget 0.3.1. The version is here so that…`, and the code taking
the version back out took "digits and dots", so it read `0.3.1.` and compared it
with `0.3.1`. Never equal. The window would have told every user their exporter
was out of date for ever, and the button that fixes it would have fixed nothing,
visibly.

Every one of the 254 checks passed while that was true, and the reason is the one
`CLAUDE.md` names. The stand-in template in `Sandbox.swift` said
`# Written by ccwidget __VERSION__` with nothing after it, so it differed from
the file that ships in exactly the way that mattered — and adding the missing
placeholders to that stand-in, done two hours earlier in this same batch, was
not enough, because the shape of the line was the defect.

What closes it is a check that installs through **the template the app ships**
and asserts the version reads back exactly. Falsified by putting both halves of
the defect back: the sentence after the version, and the parser that swallowed
its full stop. Four expectations fail.

**The rule this earns.** A stand-in for a file that ships has to differ from it
in nothing that is read back out of it. Placeholders are not enough — the shape
around them is read too.

### 16. What a pre-publication check found beyond the three questions

Three more things, none of them in the code.

**A fresh clone builds and passes.** Nobody had ever tried it: every run until
now was in the working tree, with its DerivedData, its generated project, its
`.build`. Cloned from GitHub into a temporary directory, `xcodegen generate`,
build, test — **256 checks pass**. That is the closest thing there is to "a
stranger cloned it and it worked", and it is the one check that cannot be run
from inside the working copy.

**Four broken links, all in the same place.** The outreach drafts — the messages
that ask German, Spanish, Japanese and Chinese speakers to read the
translations, written in their own languages — linked to
`../Docs/localization-review.md` from inside `Docs/localization-outreach/`,
which resolves to `Docs/Docs/…`. Wrong twice over: those files exist to be
posted as issues, and a relative link in an issue body resolves to nothing at
all. Absolute now, and the instruction at the top of each says why rather than
telling the next person to leave the link alone.

Worth noting how they were found: a script that walks every local link in every
markdown file and checks the file and the heading exist. Nineteen links, four
broken, and none of them anywhere a person would look — which is exactly where a
first visitor lands, because those four are the invitation to help.

**The CI token is read-only now, named rather than inherited.** In a public
repository anyone can open a pull request and `pull_request` runs the workflow
against their branch; the token's permissions were whatever the account settings
say. Nothing in the workflow needs to write.

**What could not be checked, and is worth doing after opening:** the repository
has no topics, so nobody browsing will find it; secret scanning and push
protection become available and should be turned on; and whether the release
asset downloads for an anonymous visitor can only be tested by being one.

### 17. The setup screen could not be put in a state, and that was the point

`OnboardingView` held `private let installer = Installer.live()`. So the first
screen every new user meets read whatever machine it was running on, and no
check could ask it anything — which is why it was 432 of the 1024 lines nothing
had executed. Section 5.2 has forbidden exactly this since it was written; the
view predates the rule being applied to views.

The installer is a parameter now, with the step alongside it, and the screen is
drawn in all four steps and all six languages.

**Two things I got wrong while writing the checks, both worth keeping.**

The bar check invented its own threshold. I wrote "200 points is well above the
longest run in any state without bars — measured at 44 — and well below the
shortest with them, at 428", and neither number was measured: I made both up
while writing the sentence. Measured, the window's bar at 100 % usage is **137**
points and the widest run without bars is **87** — a button. The rule this
project already has is that a threshold shows where it came from; a threshold
with fabricated provenance is worse than one with none, because the next reader
believes it.

And the distinctness check compared band profiles, which cannot separate
`working` from `outdated`: past an hour the figures are dimmed and gain a word,
and dimming moves nothing. It read as "two states draw the same picture", which
was false — they differ in colour. Comparing the pixels says what "draws
differently" actually means, and all six states differ.

### 18. One black tile, four attempts to reproduce it, and no cause

Recorded because the alternative is inventing an explanation.

Installing 0.3.2 through Homebrew over a self-built 0.3.1 left the desktop tile
completely black — 0.000 % ink, where a working tile is about 4.7 %. Not the
0.023 % of the 7 August case, which was antialiasing on the rounded corner:
nothing at all. Meanwhile the extension process was running, no crash report
was written, the snapshot on disk was fresh and there was exactly one container.
It stayed black for about ten minutes across two daemon restarts and an app
launch, and came back the moment the self-built copy was reinstalled.

Four controlled attempts to reproduce it, each changing one thing:

| What was varied | Tile |
|---|---|
| Signed build installed by hand, extension killed first | drew, 4.748 % |
| Signed build through Homebrew, quarantine flag present | drew, 4.762 % |
| Signed build through Homebrew, extension left running | drew, 4.757 % |
| 0.3.1 by hand, then Homebrew over it | drew, 4.741 % |

So it is not the code identity changing from ad-hoc to Developer ID, not the
quarantine attribute, not replacing the bundle under a running extension, and not
the version number changing. Those were the four hypotheses; each was tested by
changing one variable, and all four are wrong.

**What can be said:** the recovery is a reinstall, and this project already knew
that from 7 August, where removing the widget from the desktop and adding it
again was what worked. **What cannot be said is why**, and this is the place that
says so rather than the place that guesses. `Scripts/tile-probe.swift` exists
because this class of thing is invisible otherwise; it did its job twice now.

One thing worth having next time: the tile probe reports a number, and the
number here was 0.000 rather than 0.023, which is a different failure from the
one already documented. Nothing records what the probe read at the moment of
failure other than a terminal that scrolls away.

### 19. The composition checks cost four minutes, and did not have to

Adding the screen checks took the suite from 85 seconds to **330**. The cause was
`NSBitmapImageRep.colorAt(x:y:)`, which allocates an `NSColor` per pixel: the
screen checks alone read about forty million of them.

`Tests/PixelReader.swift` reads the bitmap's own bytes instead. Same numbers,
same thresholds, same falsifications failing in the same places — 266 checks in
**78 seconds**, which is under where it started.

Worth writing down because a slow suite is a suite people stop running, and
because the fix was mechanical: nothing about what is measured changed, only
what it cost to measure. The instrument was the expensive part, not the question.

### 20. The background switch was unreachable, and the documentation is why

The owner turned to Details expecting a switch and read
*"Обновление в фоне: недоступно — macOS не находит фоновую задачу"* instead.
Which is what the code said to say, and the code was built on Apple's own
description of `SMAppService.Status.notFound`: *"An error occurred and the
framework couldn't find this service."*

It is not an error. Measured with a probe inside the bundle:

    before:   notFound
    register: succeeded
    after:    enabled

`notFound` is what `mainApp` reports **before it has ever been registered** — the
state every user starts in. And unregistering afterwards leaves `notRegistered`,
not `notFound`, so the two differ only in whether the app was ever registered:
no consequence for anybody, which by this project's own rule means one state and
not two. Three now, and the switch is always offered.

**What made it worse than a wrong word.** Mapping the case to "unavailable" was
one mistake; deciding that "unavailable" should *hide the switch* was the one
that mattered. The feature was unreachable for every user, and the check that
should have caught it — every enum case produced from what `SMAppService` says —
passed, because it asserted the mapping I had written rather than the mapping the
framework implies. A check can only be as right as the fact it was built on, and
this one was built on a sentence.

**A second defect, found in the same session.** The app hid its window on any
launch the system calls not-default — and `open /Applications/CCWidget.app` from
a terminal is not-default. So the app hid itself on a launch that was plainly a
person's doing. It now requires *both* conditions: nobody asked, and the app is
registered to run at login. Whether a Finder double-click counts as default is
still unmeasured, and nothing here can simulate one.

**Three smaller things that came with it.** `SMAppService` documents
`openSystemSettingsLoginItems()`, and the code had a hand-written
`x-apple.systempreferences:` URL that would break silently the day Apple renamed
the pane — the documented call was on the same page, unread. The bundle carried
an empty `Contents/Library/LaunchAgents` left by a copy phase for the agent that
turned out to be impossible; a build step removes it. And the window's
login-item state is logged at `notice` rather than `info`, because `.info` is
gone from the log within minutes and this project has been caught by that twice.

### 21. The window said the same thing twice, and a screenshot found it

Turning background updates on printed *"включено — плитка обновляется в пределах
минуты"* under the switch, where it belongs, and again at the foot of Details,
where the notice line lives. My doing: `setBackgroundUpdates` put the new state
into `notice`.

Nothing caught it. There is now an instrument that would: two identical
sentences render as identical rows of ink at the same offset, so a band
fingerprint finds them. Measured — the shipped shape gives 18 bands with one
repeated, the fixed one 17 with none, and all six window states none.

**Two things about building that instrument are worth more than the instrument.**

The first reproduction found nothing, because the notice is drawn inside Details
and the fixture had Details collapsed. An instrument that reports "clean" about a
defect standing in front of it is worse than no instrument, and the only reason
it was caught is that the reproduction was checked against a known-bad case
before being trusted. That is now a check of its own: *the instrument notices a
repeated line*. It fails if the instrument ever stops working.

And the check that asserted the duplication was **rewritten, not joined**. It
said the notice must contain "within a minute" — it asserted the defect. Two
checks disagreeing about one thing is worse than one that was wrong, which
`CLAUDE.md` says in as many words.

The notice now exists for the one outcome the line beside the switch cannot
show: the framework refusing. Not for approval — the line says it is waiting and
a button beside it goes there.

### 22. "закрылось" was read as "your window closed"

The owner closed an IDE window, looked at the tile, saw *"Использовано за
5 часов — закрылось"*, and asked why closing a window had done that.

The coincidence was accidental — the five-hour window reset at 18:30, which the
snapshot confirms (`0 %`, next reset 23:30, where minutes earlier it was `10 %`
resetting at 18:30). The misreading was not accidental. On a screen, «окно» is a
program's window, so «закрылось» attaches to that and not to a limit period.

Russian is now «сброшено», which cannot mean an application window and speaks
the vocabulary the rest of the interface already uses — the week «сбрасывается»
on Thursday. Measured against the same 66 pt slot: 52 pt, where «закрылось» took
55 and «период истёк» takes 69, which is why it stays one word.

`closed`, `beendet`, `終了`, `已结束` stay: three of them already say *ended*
rather than *closed*, and no misreading has been observed for any of them.
Spanish `cerrada` is the same class as the old Russian, and changing it by
analogy would be guessing on a native reader's behalf — recorded in `SPEC` and
waiting for an observation.

**What this says about copy.** A word that fits, is honest, and is announced
correctly to VoiceOver can still be read as being about something else. No check
can find that; the only instrument is somebody reading it who did not write it.
The two width checks and the announcement baseline all passed, and all of them
were about the word being the right size and in the right order.

### 23. A fresh snapshot can carry stale limits — 13 steps backwards, measured

Chasing why the five-hour row said "closed" turned up something bigger than the
wording. The limits arrive with a model's reply and sit in the session until the
next one, so a session writes the reading **it** last saw. `capturedAt` is fresh;
the numbers need not be.

Measured on this machine's own history: 522 rows, 7 weekly windows, **13 steps
backwards inside a single window** — the largest 27 % → 24 % six minutes apart on
7 August. Consumption cannot fall before a reset, and consistent rounding of a
fractional percentage cannot lose three points.

Nothing is discarded on that basis. The forecast gates on how well its line
describes the points, so an older reading costs confidence rather than producing
a confident wrong answer. What it must not do is pass in silence: a reload that
arrives with a reading gone backwards now logs `older reading: 7d`, and the check
that would otherwise cry wolf every five hours is the one that matters — after a
reset the percentage is *supposed* to fall, so the comparison is per window, not
per number.

**How this was nearly missed twice.** The first pass over the history reported
zero backwards steps, because the field is `sevenDay` and the script looked for
`week`/`weekPercent`/`usedPercentage`. Every row read as "no value", every
comparison was skipped, and the answer came back clean. `CLAUDE.md` has the rule
this breaks by name: the same result on knowingly different inputs means the
inputs are not reaching the instrument. The second pass asserts the field names
before measuring anything.

### 24. The reload log said nothing about the reload

`widget reload #22 (snapshot changed)` was the whole record. Answering "was the
five-hour window already expired in that snapshot?" was impossible from it — the
order of events had to be reconstructed from timestamps in Claude Code's own
prompt history.

The line now carries what the tile drew: `moved 5h,context · five-hour expired ·
week open`. No values in it — percentages are raw fields, kept `.private`, and a
`.private` value read back without a logging profile is redacted, so a line built
from them would answer nothing.

Two things fell out of writing it. The signature became a type instead of a
joined string, because the string could answer "is this different" and nothing
else; naming *what* changed meant splitting it back apart and trusting the pieces
still lined up with their names. And `budget window closed` was renamed to
`reload budget elapsed` — it is about the minute-long reload ration, not about a
limit window, and the collision of words misled the investigation that found it.

### 25. The bundle could not say which build it was

Twice in one day the question "which build is this?" had no answer from the
build. The installed app reported `0.3.2` and contained work the `v0.3.2` tag
does not have, so it took `strings` on the binary and the modification date of
the executable — and the owner had asked the same question hours earlier about a
file that was meant to be inside the bundle.

A version number cannot answer it. `MARKETING_VERSION` moves once per release, so
every build between two releases wears the number of the release before it. The
commit is the identifying part, and it now reaches the bundle through
`CCWidgetCommit`, stamped by `Scripts/release.sh` and empty everywhere else, with
the window's Details naming it in a row of its own.

Three readings, all three produced by checks: a release names its commit, an
ordinary build says it is not a release, and a bundle whose keys are gone says
`unknown`. Measured rather than assumed — an empty build setting leaves the key
present with an empty value, which is why the test for "no commit" is emptiness
and not `nil`.
